# Глава 6.4. Проектирование API и версионирование

> Модуль 6. Взаимодействие сервисов и API
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

API — это *контракт* между частями системы ([6.2](06-02-rest-grpc-graphql.md)) и с внешним миром. Контракт переживает реализацию и связывает стороны ([3.1](../03-dekompoziciya-ddd/03-01-svyazannost-sceplenie-connascence.md)): изменишь его неудачно — сломаешь всех потребителей. И в отличие от внутреннего кода, опубликованный API почти необратим (односторонняя дверь, [0.1](../00-professiya/00-01-chto-takoe-arhitektura.md)): у публичного API могут быть тысячи потребителей, которых ты не контролируешь и не можешь обновить. Поэтому проектирование API и его *эволюция без поломок* — критический навык архитектора.

Глава даёт принципы хорошего контракта (любого стиля из [6.2](06-02-rest-grpc-graphql.md)) и — главное — как менять контракт, *не ломая потребителей*: обратная совместимость, стратегии версионирования, управление изменением. Прямое продолжение: контракт и связанность, односторонние двери, эволюция ([Модуль 11](../11-ocenka-evolyuciya/README.md) впереди).

Установка: **API — это публичный контракт-обязательство; проектируй его как надолго и эволюционируй обратно совместимо, потому что ломающее изменение бьёт по всем потребителям, которых ты не контролируешь.**

## 2. Теория

### 2.1. API — это контракт и обязательство

Опубликованный API — *обещание* потребителям: «вот форма запроса/ответа, она будет работать». Потребители строят на нём код. Контракт *связывает* ([3.1](../03-dekompoziciya-ddd/03-01-svyazannost-sceplenie-connascence.md)): потребитель зависит от формы API. Чем больше потребителей (особенно внешних, неконтролируемых), тем дороже его менять — это сильная односторонняя дверь ([0.1](../00-professiya/00-01-chto-takoe-arhitektura.md)). Внутренний API между своими сервисами эволюционировать легче (потребителей знаешь, можешь скоординировать); публичный — почти невозможно ломать.

### 2.2. Принципы хорошего API

- **Ориентирован на потребителя, не на реализацию.** API выражает *потребности клиента* и доменные понятия (единый язык, [3.3](../03-dekompoziciya-ddd/03-03-ddd-strategicheskiy.md)), а не внутреннее устройство БД/кода. Утечка внутренней модели в API связывает потребителей с твоими внутренностями (нарушение инкапсуляции, §2.2, [3.3](../03-dekompoziciya-ddd/03-03-ddd-strategicheskiy.md)).
- **Грубогранулярный, не болтливый.** Один осмысленный вызов вместо множества мелких ([3.5](../03-dekompoziciya-ddd/03-05-granicy-servisov-i-moduley.md), [4.1](../04-raspredelennye-sistemy/04-01-zabluzhdeniya-i-setevye-osnovy.md)) — особенно через сеть.
- **Согласованность и предсказуемость.** Единые соглашения (именование, форматы ошибок, пагинация) по всему API — меньше когнитивной нагрузки.
- **Явные ошибки.** Чёткие коды/формы ошибок, отличающие «ошибка клиента» (4xx) от «ошибка сервера» (5xx — повтор уместен, [4.4](../04-raspredelennye-sistemy/04-04-patterny-ustoychivosti.md)).
- **Минимальная поверхность.** Выставляй только нужное: меньше поверхность → меньше связанность и поверхность атаки ([Модуль 7](../07-bezopasnost/README.md)).
- **Идемпотентность где уместно** ([4.5](../04-raspredelennye-sistemy/04-05-raspredelennye-tranzakcii-saga.md)): операции, которые будут повторять, делай идемпотентными (ключ идемпотентности).

### 2.3. Обратная совместимость — ядро эволюции

Ключ к изменению API без поломок — **обратная совместимость**: новый сервер работает со *старыми* клиентами. Изменения делятся на:

- **Несломающие (backward-compatible):** *добавить* необязательное поле, новый эндпоинт, новое значение enum (если клиент терпим к неизвестным) — старые клиенты не замечают. Безопасно.
- **Сломающие (breaking):** *удалить/переименовать* поле, изменить тип, сделать поле обязательным, изменить семантику, удалить эндпоинт — старые клиенты ломаются. Требуют версионирования (§2.4).

Правило: **добавляй, не ломай.** Большинство эволюций можно сделать аддитивно (новые необязательные поля/эндпоинты), избегая версионирования вовсе.

### 2.4. Толерантный читатель (tolerant reader)

Принцип, снижающий хрупкость: **потребитель должен быть толерантен** — игнорировать неизвестные поля, не падать от добавлений, читать только то, что ему нужно (принцип робастности). Тогда сервер может *добавлять* поля, не ломая клиентов. Хрупкий клиент (падает от любого нового поля, требует точного соответствия) делает невозможной даже аддитивную эволюцию. Толерантность потребителей — условие безопасной эволюции контракта.

### 2.5. Стратегии версионирования

Когда сломающее изменение неизбежно — нужна версия. Стратегии:

- **В URL** (`/v1/orders`, `/v2/orders`) — явно, просто, видно; распространено в REST.
- **В заголовке** (`Accept: application/vnd.api.v2+json`) — чище URL, но менее видно.
- **В схеме** (protobuf/GraphQL): protobuf эволюционирует через правила совместимости полей (не переиспользовать номера, новые поля опциональны); GraphQL предпочитает *аддитивную* эволюцию + deprecation полей вместо версий.

Принципы версионирования:
- **Поддерживай старую версию параллельно** некоторое время (старые клиенты ещё на ней), затем deprecation с понятным сроком и миграцией.
- **Не плоди версии бездумно** — каждая версия = поддержка параллельно (цена). Версионируй только при реальном сломающем изменении; аддитивное — без версии.
- **Deprecation, не резкое удаление:** помечай устаревшее, дай срок и путь миграции, предупреди потребителей.

### 2.6. Внутренний vs публичный API

Эволюция зависит от контроля над потребителями:
- **Внутренний** (между своими сервисами): потребителей знаешь, можешь скоординировать релизы — эволюция проще, иногда даже сломающие изменения согласованно. Но не злоупотребляй (распределённый монолит, [2.3](../02-stili/02-03-mikroservisy-i-soa.md)).
- **Публичный/сторонний:** потребителей не контролируешь, не можешь обновить — ломать почти нельзя; обратная совместимость и долгая поддержка версий критичны. Здесь контракт — самое обязывающее обещание.

## 3. Подходы

**Подход 1.** Проектируй API под потребителя и домен (единый язык, [3.3](../03-dekompoziciya-ddd/03-03-ddd-strategicheskiy.md)), не под внутреннюю реализацию; не пускай внутреннюю модель наружу (§2.2).

**Подход 2.** Делай контракт грубогранулярным ([3.5](../03-dekompoziciya-ddd/03-05-granicy-servisov-i-moduley.md)), согласованным, с явными ошибками и минимальной поверхностью; идемпотентность где повторяют ([4.5](../04-raspredelennye-sistemy/04-05-raspredelennye-tranzakcii-saga.md)).

**Подход 3.** Эволюционируй аддитивно: «добавляй, не ломай» (§2.3). Большинство изменений — новые необязательные поля/эндпоинты без версии.

**Подход 4.** Делай потребителей толерантными (игнорировать неизвестное, §2.4) — это условие безопасной аддитивной эволюции.

**Подход 5.** Версионируй только при неизбежном сломающем изменении; не плоди версии (цена параллельной поддержки, §2.5).

**Подход 6.** Не удаляй резко — deprecation со сроком, путём миграции, предупреждением потребителей.

**Подход 7.** Различай внутренний (можно координировать) и публичный (ломать почти нельзя) API; для публичного — максимум обратной совместимости и долгой поддержки (§2.6).

## 4. Пример кода: аддитивная эволюция vs сломающее изменение

```typescript
// ВЕРСИЯ 1 контракта заказа.
interface OrderResponseV1 {
  id: string;
  total: number;
  status: string;
}

// НЕСЛОМАЮЩЕЕ изменение: ДОБАВИЛИ необязательные поля (§2.3). Старые клиенты их игнорируют
// (толерантный читатель, §2.4) — версия НЕ нужна.
interface OrderResponseV1Plus {
  id: string;
  total: number;
  status: string;
  currency?: string; // новое необязательное поле — старый клиент его не читает, не ломается
  estimatedDelivery?: string; // ещё одно добавление — безопасно
}

// СЛОМАЮЩЕЕ изменение: переименовали total -> amount, изменили тип status. Старые клиенты СЛОМАЮТСЯ.
// => нужна НОВАЯ версия (§2.5), старая поддерживается параллельно.
interface OrderResponseV2 {
  id: string;
  amount: Money; // переименование + смена типа = сломающее
  status: "draft" | "confirmed" | "shipped"; // смена строки на enum = сломающее
}

// Сервер отдаёт обе версии параллельно; старая помечена deprecated со сроком (§2.5, подход 6).
function getOrder(version: "v1" | "v2", id: string) {
  return version === "v2" ? toV2(id) : toV1(id); // v1 поддерживается, пока клиенты не мигрируют
}

// ТОЛЕРАНТНЫЙ ЧИТАТЕЛЬ (§2.4, подход 4): клиент берёт ТОЛЬКО нужные поля, игнорируя остальные.
function readOrder(raw: any): { id: string; total: number } {
  return { id: raw.id, total: raw.total }; // не падает от новых/неизвестных полей сервера
}
```

**Суть:** добавление необязательных полей — несломающее (толерантный клиент игнорирует, версия не нужна); переименование/смена типа/семантики — сломающее, требует новой версии с параллельной поддержкой и deprecation старой. Правило «добавляй, не ломай» (§2.3) + толерантные потребители (§2.4) позволяют эволюционировать без версионирования в большинстве случаев.

## 5. Развёрнутый кейс: эволюция API заказов

Сервис заказов имеет API с внутренними сервисами (внутренний) и с партнёрами (публичный). Нужно развивать его годами, не ломая.

**Аддитивная эволюция (без версий).** Большинство изменений делали аддитивно (подход 3): добавили `currency`, `estimatedDelivery`, новый эндпоинт `/orders/{id}/tracking` — всё *необязательное/новое*. Потребители (толерантные, §2.4) не заметили; версионирование не понадобилось. Так прошли 90% изменений без боли.

**Неизбежное сломающее изменение.** Понадобилось сменить `total: number` на `amount` со структурой `Money` (сумма + валюта) — переименование и смена типа, *сломающее* (§2.3). Решение: ввели `/v2/orders` с новым контрактом, *оставив* `/v1/orders` работать (§2.5). Внутренние сервисы (контролируемые, §2.6) скоординированно перешли на v2 за пару недель. Партнёрам (публичный, §2.6) дали deprecation v1 с *длинным* сроком (полгода), документацию миграции и предупреждения — нельзя резко ломать тех, кого не контролируешь. Через полгода v1 отключили.

**Ошибка, которую избежали.** Соблазн был «просто поменять `total` на `amount` в одном API» — это сломало бы всех партнёров мгновенно (односторонняя дверь, [0.1](../00-professiya/00-01-chto-takoe-arhitektura.md)), вызвав инциденты у тысяч потребителей, которых не обновить. Версионирование + параллельная поддержка + deprecation превратили катастрофу в управляемую миграцию.

**Контрпример — переверсионирование.** Другая команда заводила *новую версию на каждое* мелкое изменение (`v3`, `v4`, `v5`…), включая аддитивные. Получили зоопарк версий, каждую надо поддерживать параллельно (цена, §2.5), потребители путались. Лечение: аддитивные изменения — без версии (подход 3, 5); версия — только при реальном сломающем.

**Мораль:** «добавляй, не ломай» + толерантные потребители убирают нужду в версиях в большинстве случаев; версионируй только неизбежно сломающее, с параллельной поддержкой и deprecation; для публичного API обратная совместимость критична, ибо потребителей не контролируешь.

## 6. Антипаттерны и ловушки

**Утечка внутренней модели в API.** API повторяет схему БД/внутренние сущности (§2.2, [3.3](../03-dekompoziciya-ddd/03-03-ddd-strategicheskiy.md)): потребители связаны с твоими внутренностями, любое внутреннее изменение ломает контракт. Проектируй под потребителя/домен.

**Сломающее изменение без версии.** Переименовать/удалить поле, сменить тип/семантику в существующем API (кейс): мгновенно ломает потребителей, особенно неконтролируемых публичных (односторонняя дверь, [0.1](../00-professiya/00-01-chto-takoe-arhitektura.md)). Версионируй.

**Хрупкий потребитель.** Клиент падает от неизвестных полей, требует точного соответствия (§2.4): делает невозможной даже аддитивную эволюцию. Будь толерантным читателем.

**Переверсионирование.** Новая версия на каждое мелкое (даже аддитивное) изменение (кейс): зоопарк версий, цена параллельной поддержки, путаница. Версионируй только сломающее.

**Резкое удаление без deprecation.** Выключить старую версию/поле без срока и предупреждения (§2.5): ломает не успевших мигрировать. Deprecation со сроком и путём миграции.

**Болтливый API.** Множество мелких эндпоинтов вместо грубогранулярных ([3.5](../03-dekompoziciya-ddd/03-05-granicy-servisov-i-moduley.md), [4.1](../04-raspredelennye-sistemy/04-01-zabluzhdeniya-i-setevye-osnovy.md)): потребители делают много вызовов. Укрупняй контракт.

**Игнор различия внутренний/публичный.** Ломать публичный API так же легко, как внутренний (§2.6): но публичных потребителей не обновить. Для публичного — максимум совместимости.

## 7. Ключевые выводы (чеклист)

- [ ] API — **публичный контракт-обязательство**, переживает реализацию, связывает потребителей; публичный API — сильная **односторонняя дверь** ([0.1](../00-professiya/00-01-chto-takoe-arhitektura.md)).
- [ ] Хороший API: **под потребителя/домен** (не реализацию), грубогранулярный, согласованный, явные ошибки, минимальная поверхность, идемпотентность где повторяют.
- [ ] **Обратная совместимость** — ядро эволюции: «**добавляй, не ломай**» (новые необязательные поля/эндпоинты — несломающие).
- [ ] **Толерантный читатель** (игнорировать неизвестное) — условие безопасной аддитивной эволюции.
- [ ] **Версионируй только неизбежно сломающее** (переименование/тип/семантика/удаление); аддитивное — без версии. Не плоди версии.
- [ ] **Deprecation, не резкое удаление:** параллельная поддержка, срок, путь миграции, предупреждение.
- [ ] **Публичный API** ломать почти нельзя (потребителей не контролируешь) — максимум совместимости; внутренний эволюционировать проще.

## 8. Упражнения и вопросы

1. Почему API — это обязательство и односторонняя дверь? Чем эволюция публичного API отличается от внутреннего?
2. Какие изменения несломающие, а какие сломающие? Сформулируй правило «добавляй, не ломай» и роль толерантного читателя.
3. Когда нужно версионирование, а когда нет? Почему переверсионирование — антипаттерн?
4. Возьми API в своей системе. Утекает ли в него внутренняя модель? Толерантны ли потребители? Как делались последние изменения — аддитивно или ломающе?
5. Найди недавнее изменение API. Было ли оно сломающим? Можно ли было сделать аддитивно? Как обработали совместимость?
6. Возьми код-пример из раздела §4: предложи ещё одно сломающее изменение (например, разбить `status` на `status` + `subStatus`) и покажи, как сделать его (а) аддитивно, если возможно, или (б) через версию с deprecation, если нет.
7. Спроектируй стратегию версионирования для публичного API: как версионируешь, как долго поддерживаешь старое, как объявляешь deprecation и помогаешь миграции. Чем отличалась бы стратегия для внутреннего API?
