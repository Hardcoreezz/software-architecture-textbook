# Глава 6.4. Проектирование API и версионирование

> Модуль 6. Взаимодействие сервисов и API
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

API — это контракт между частями системы и с внешним миром, в каком бы стиле из [6.2](06-02-rest-grpc-graphql.md) он ни был сделан. Неудачно изменишь контракт — сломаешь всех, кто на нём построен. Внутренний код можно поправить вместе со всеми вызывающими, а у публичного API бывают тысячи потребителей, которых ты не контролируешь и не можешь обновить. Поэтому архитектору нужны два навыка: спроектировать контракт надолго и развивать его, не ломая потребителей.

---

## 2. Теория

### 2.1. API — это контракт и обязательство

Опубликованный API — обещание потребителям: «вот форма запроса и ответа, и она будет работать». Код за API можно переписать, а форма остаётся: потребители построили на ней свой код и зависят от неё ([3.1](../03-dekompoziciya-ddd/03-01-svyazannost-sceplenie-connascence.md)). Чем больше потребителей, особенно внешних, тем дороже изменение: публичный API — сильная односторонняя дверь, решение, которое почти нельзя отменить ([0.1](../00-professiya/00-01-chto-takoe-arhitektura.md)).

### 2.2. Принципы хорошего API

- **Под потребителя, а не под реализацию.** API говорит на языке клиента и домена (единый язык, [3.3](../03-dekompoziciya-ddd/03-03-ddd-strategicheskiy.md)), а не повторяет устройство БД и кода. Внутренняя модель, утёкшая наружу, связывает потребителей с твоими внутренностями (нарушение инкапсуляции, [3.2](../03-dekompoziciya-ddd/03-02-principy-dekompozicii.md)).
- **Грубогранулярный, а не болтливый:** один осмысленный вызов вместо множества мелких, особенно через сеть ([3.5](../03-dekompoziciya-ddd/03-05-granicy-servisov-i-moduley.md), [4.1](../04-raspredelennye-sistemy/04-01-zabluzhdeniya-i-setevye-osnovy.md)).
- **Согласованный:** единые именование, формат ошибок и пагинация по всему API снижают когнитивную нагрузку.
- **С явными ошибками:** коды отличают ошибку клиента (4xx) от ошибки сервера (5xx). Ошибка сервера часто временная, и идемпотентную операцию после неё можно повторить ([4.4](../04-raspredelennye-sistemy/04-04-patterny-ustoychivosti.md)).
- **С минимальной поверхностью:** выставляй только нужное, тогда меньше и связанность, и поверхность атаки ([Модуль 7](../07-bezopasnost/README.md)).
- **Идемпотентный, где уместно:** операции, которые будут повторять, делай идемпотентными, например через ключ идемпотентности ([4.5](../04-raspredelennye-sistemy/04-05-raspredelennye-tranzakcii-saga.md)).

### 2.3. Обратная совместимость — ядро эволюции

**Обратная совместимость** (backward compatibility) — новый сервер работает со старыми клиентами.

- **Несломающие изменения:** новое необязательное поле, новый эндпоинт, новое значение enum (если клиент терпим к неизвестным значениям). Старые клиенты их не замечают.
- **Сломающие (breaking):** удалить или переименовать поле, сменить его тип или семантику, сделать поле запроса обязательным, удалить эндпоинт.

Правило: **добавляй, не ломай.** Большинство изменений делается аддитивно, без версии. Даже переименование можно провести так: добавить новое поле рядом со старым, а старое пометить устаревшим (deprecated) и удалить, когда клиенты перейдут на новое. Само удаление — тоже сломающее изменение, поэтому его проводят через deprecation со сроком (§2.5). Новая версия нужна, когда аддитивно провести изменение нельзя или слишком дорого.

### 2.4. Толерантный читатель (tolerant reader)

**Толерантный читатель** — потребитель, который читает только нужные ему поля, игнорирует неизвестные и не падает от добавлений (принцип робастности). Только с такими потребителями сервер может добавлять поля, не ломая клиентов.

### 2.5. Стратегии версионирования

Если сломающее изменение нельзя или слишком дорого провести аддитивно, нужна новая версия. Её указывают:

- **в URL** (`/v1/orders`, `/v2/orders`) — явно и просто, распространено в REST;
- **в заголовке** (`Accept: application/vnd.example.v2+json`) — URL чище, но версию хуже видно;
- **в схеме**: protobuf эволюционирует по правилам совместимости полей (номера не переиспользуют, новые поля опциональны), а GraphQL вместо версий предпочитает аддитивную эволюцию и deprecation полей.

Каждую версию приходится поддерживать параллельно с остальными, поэтому её заводят только для реального сломающего изменения. Старую держат, пока клиенты мигрируют, и выводят через **deprecation**: помечают устаревшей, объявляют срок, дают путь миграции и предупреждают потребителей. Резкое отключение ломает тех, кто не успел мигрировать.

### 2.6. Внутренний vs публичный API

Свобода изменений зависит от контроля над потребителями.

- **Внутренний** API: потребителей знаешь и можешь скоординировать релизы, поэтому иногда допустимы даже согласованные сломающие изменения. Но если сервисы приходится выкатывать только вместе, это уже распределённый монолит ([2.3](../02-stili/02-03-mikroservisy-i-soa.md)).
- **Публичный** API: потребителей не контролируешь и не обновишь, поэтому ломать почти нельзя, а обратная совместимость и долгая поддержка версий обязательны.

---

## 3. Подходы

**Подход 1.** Проектируй контракт под потребителя и домен по принципам §2.2 и не выпускай наружу внутреннюю модель.

**Подход 2.** Меняй API аддитивно и требуй от потребителей толерантного чтения (§2.3, §2.4): тогда большинство изменений обходится без версии.

**Подход 3.** Версию заводи только для сломающего изменения, которое нельзя или слишком дорого провести аддитивно; старую поддерживай параллельно и выводи через deprecation (§2.5).

**Подход 4.** Прежде чем менять API, определи, внутренний он или публичный: от этого зависит, можно ли договориться с потребителями или ломать почти нельзя (§2.6).

---

## 4. Пример кода: аддитивная эволюция vs сломающее изменение

```typescript
type Money = { value: number; currency: string };

// Версия 1 контракта заказа.
interface OrderResponseV1 {
  id: string;
  total: number;
  status: string;
}

// НЕСЛОМАЮЩЕЕ изменение (§2.3): добавили необязательные поля.
// Толерантные клиенты (§2.4) их игнорируют — версия не нужна.
interface OrderResponseV1Plus {
  id: string;
  total: number;
  status: string;
  currency?: string;
  estimatedDelivery?: string;
}

// СЛОМАЮЩЕЕ изменение: переименовали total -> amount и сменили тип status.
// Старые клиенты сломаются => новая версия (§2.5), старая поддерживается параллельно.
interface OrderResponseV2 {
  id: string;
  amount: Money; // переименование + смена типа
  status: { code: "draft" | "confirmed" | "shipped"; since: string }; // строка -> объект
}

declare function toV1(id: string): OrderResponseV1Plus;
declare function toV2(id: string): OrderResponseV2;

// Сервер отдаёт обе версии; v1 помечена deprecated со сроком (§2.5).
function getOrder(version: "v1" | "v2", id: string) {
  return version === "v2" ? toV2(id) : toV1(id); // v1 живёт, пока клиенты не мигрируют
}

// ТОЛЕРАНТНЫЙ ЧИТАТЕЛЬ (§2.4): берёт только нужные поля и не падает от новых.
function readOrder(raw: any): { id: string; total: number } {
  return { id: raw.id, total: raw.total };
}
```

**Суть:** на ответе V1Plus `readOrder` работает, а на V2 молча получит `total: undefined`. Толерантность спасает от добавлений, но не от переименования: для него нужна новая версия или новое поле рядом со старым (§2.3).

---

## 5. Развёрнутый кейс: эволюция API заказов

Сервис заказов отдаёт API внутренним сервисам и партнёрам, и развивать его нужно годами.

**Аддитивная эволюция.** Большинство изменений сделали аддитивно (подход 2): добавили `currency`, `estimatedDelivery` и эндпоинт `/orders/{id}/tracking`. Толерантные потребители ничего не заметили. Так, без версий, прошли 90% изменений.

**Сломающее изменение.** Понадобилось заменить `total: number` на `amount` типа `Money` (сумма и валюта). Можно было добавить `amount` рядом с `total`, но тогда партнёры годами получали бы два поля суммы, которые надо держать согласованными, а удалять `total` всё равно пришлось бы через deprecation. Поэтому ввели `/v2/orders`, оставив работать `/v1/orders`. Внутренние сервисы скоординированно перешли на v2 за пару недель. Партнёрам объявили deprecation v1 со сроком в полгода, дали документацию миграции и предупреждения; через полгода v1 отключили.

**Вывод.** Был соблазн «просто поменять `total` на `amount`» в существующем API. Это мгновенно сломало бы интеграции всех партнёров — тысячи потребителей, которых не обновить. Версия с параллельной поддержкой и deprecation превратила возможную катастрофу в управляемую миграцию.

---

## 6. Антипаттерны и ловушки

**Утечка внутренней модели в API.** API повторяет схему БД или внутренние сущности, и любое внутреннее изменение ломает контракт.

**Сломающее изменение без версии.** Переименовать или удалить поле, сменить его тип или семантику прямо в работающем API — значит мгновенно сломать потребителей (кейс в §5). Переименование проводи аддитивно (новое поле рядом со старым), а удаление и смену типа — через deprecation или новую версию.

**Хрупкий потребитель.** Клиент падает от любого нового поля или требует точного соответствия схеме. С такими потребителями невозможна даже аддитивная эволюция (§2.4).

**Переверсионирование.** Новая версия на каждое мелкое изменение, включая аддитивные: `v3`, `v4`, `v5`… Получается зоопарк версий: каждую надо поддерживать параллельно, а потребители путаются, какую брать.

---

## 7. Ключевые выводы (чеклист)

- [ ] API — **контракт-обязательство**: переживает реализацию и связывает потребителей.
- [ ] Хороший API — **под потребителя и домен**, грубогранулярный, согласованный, с явными ошибками, минимальной поверхностью и идемпотентностью там, где повторяют.
- [ ] **Добавляй, не ломай**; потребители — **толерантные читатели**.
- [ ] **Версия — только для сломающего изменения**, которое нельзя или слишком дорого провести аддитивно.
- [ ] **Deprecation, а не резкое удаление:** параллельная поддержка, срок, путь миграции.
- [ ] **Публичный API** ломать почти нельзя; внутренний меняют согласованно с потребителями.

## 8. Упражнения и вопросы

1. Почему API — обязательство и односторонняя дверь? Чем эволюция публичного API отличается от внутреннего?
2. Какие изменения несломающие, а какие сломающие? Сформулируй правило «добавляй, не ломай» и роль толерантного читателя.
3. Когда версионирование нужно, а когда нет? Почему переверсионирование — антипаттерн?
4. Возьми API своей системы. Утекает ли в него внутренняя модель? Толерантны ли потребители?
5. Найди недавнее изменение API. Было ли оно сломающим, можно ли было сделать его аддитивно и как обработали совместимость?
6. В примере из §4 предложи ещё одно сломающее изменение (например, разбить `status` на `status` + `subStatus`) и покажи, как провести его аддитивно или, если нельзя, через версию с deprecation.
7. Спроектируй стратегию версионирования для публичного API: где указываешь версию, сколько поддерживаешь старую, как объявляешь deprecation и помогаешь с миграцией. Чем отличалась бы стратегия для внутреннего API?

## 9. Что почитать дальше

- **Google API Design Guide (AIP) и Microsoft REST API Guidelines.** Принципы хорошего API, согласованность, ошибки (§2.2).
- **Martin Fowler. «Tolerant Reader» и материалы про эволюцию контрактов.** Принцип робастности (§2.4).
- **Документация protobuf и GraphQL по эволюции схемы и deprecation.** Аддитивная эволюция строгих контрактов (§2.5).
- **Sam Newman. «Building Microservices», главы о контрактах и совместимости.** Версионирование, consumer-driven contracts, внутренний и публичный API (§2.6).
- **Neal Ford et al.. «Building Evolutionary Architectures».** Эволюция как свойство архитектуры; мост к Модулю 11.
