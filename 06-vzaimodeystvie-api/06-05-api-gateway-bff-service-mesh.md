# Глава 6.5. API Gateway, BFF, Service Mesh

> Модуль 6. Взаимодействие сервисов и API
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

Когда система — это много сервисов (Модуль 2–3), общающихся синхронно и асинхронно (6.1–6.3) через API (6.2, 6.4), возникают сквозные задачи на *границах* и в *сети между сервисами*: где единая точка входа для клиентов? кто решает аутентификацию, маршрутизацию, ограничение частоты? как клиенту не звать десять сервисов? как управлять таймаутами, повторами, mTLS, трейсингом между сервисами, не вписывая это в каждый сервис? Ответы — три инфраструктурных паттерна: **API Gateway** (единая точка входа), **BFF** (API под конкретного клиента) и **Service Mesh** (управление взаимодействием между сервисами).

Эти паттерны часто путают и применяют не к месту: Gateway раздувают в god-компонент с бизнес-логикой, BFF плодят без нужды, Mesh тащат в систему из трёх сервисов (операционная цена). Глава даёт каждому чёткую роль и границы. Прямое продолжение: устойчивость (4.4 — mesh выносит её на инфраструктуру), API-стили (6.2), безопасность (Модуль 7 впереди), эксплуатация (Модуль 9 впереди). Это финал Модуля 6.

Установка: **Gateway, BFF, Mesh — инфраструктура для сквозных задач границы и межсервисной сети; каждый решает свою задачу, не дублируй и не раздувай их, и применяй по нужде, а не по моде.**

---

## 2. Теория

### 2.1. API Gateway: единая точка входа

**API Gateway** — единая точка входа для внешних клиентов, перед набором сервисов. Клиент бьёт в шлюз, шлюз маршрутизирует к нужным сервисам. Снимает со *всех* сервисов сквозные пограничные заботы:

- маршрутизация запросов к сервисам;
- аутентификация/авторизация на входе (Модуль 7);
- ограничение частоты (rate limiting), квоты;
- TLS-терминация, агрегация ответов нескольких сервисов;
- кэширование на границе (5.4), логирование, метрики входа.

Зачем: без шлюза каждый сервис сам реализует аутентификацию, rate limiting, TLS — дублирование и несогласованность; клиенту надо знать адреса всех сервисов. Шлюз централизует пограничные заботы и даёт клиенту одну точку. Связь с EIP (5.6): шлюз — это Content-Based Router + сквозные фильтры на границе.

**Граница ответственности (критично):** шлюз делает *сквозные пограничные* задачи, *не бизнес-логику*. Если в шлюз затекает бизнес-логика — он становится god-компонентом и узким горлышком (повтор ошибки ESB/умной трубы из 2.3, 5.6 — антипаттерн). Шлюз — тонкий, бизнес-логика в сервисах.

### 2.2. BFF: Backend for Frontend

**BFF** — отдельный API-слой *под конкретный тип клиента* (мобильный, веб, партнёрский). Вместо одного общего API, обслуживающего всех (компромисс для всех — over/under-fetching, 6.2), у каждого клиента *свой* BFF, заточенный под *его* нужды: мобильный BFF отдаёт компактные ответы, веб BFF — богатые, агрегируя данные из внутренних сервисов под конкретные экраны.

Зачем: разные клиенты имеют разные потребности в данных (6.2, кейс GraphQL); общий API либо переусложнён, либо неоптимален для каждого. BFF позволяет каждому клиенту иметь оптимальный API, развиваемый *командой этого клиента*. Связь с 6.2: BFF часто реализуют через GraphQL (клиент-driven) или агрегирующий REST; внутри зовут сервисы по gRPC (6.2, сосуществование).

**Граница:** BFF — *адаптация под клиента и агрегация*, не бизнес-логика (она в сервисах). BFF на клиента, а не «BFF на всё».

### 2.3. Service Mesh: управление межсервисной сетью

**Service Mesh** — инфраструктурный слой, управляющий взаимодействием *между сервисами* (не на границе с клиентом, а внутри). Реализуется обычно через *сайдкары* (прокси рядом с каждым сервисом), перехватывающие весь межсервисный трафик. Выносит на инфраструктуру сквозные *сетевые* заботы, которые иначе вписывались бы в каждый сервис:

- устойчивость: таймауты, повторы, circuit breaker (4.4!) — на уровне mesh, не в коде сервиса;
- mTLS (шифрование/аутентификация между сервисами, zero trust — Модуль 7);
- service discovery, балансировка, маршрутизация (canary, A/B);
- наблюдаемость: распределённый трейсинг, метрики межсервисного трафика (Модуль 8).

Зачем: устойчивость (4.4), безопасность, наблюдаемость межсервисного трафика — *сквозные* и одинаковые для всех сервисов; вписывать их в каждый сервис на каждом языке — дублирование. Mesh выносит их в инфраструктуру (сайдкары), единообразно и вне кода. Связь с 4.4: паттерны устойчивости, которые мы кодировали вручную, mesh даёт декларативно на уровне платформы.

### 2.4. Три разные задачи — не путать

Чёткое разделение:
- **API Gateway** — *граница с внешними клиентами* (вход в систему): маршрутизация, аутентификация, rate limiting на входе.
- **BFF** — *API под конкретного клиента* (часто за/как часть шлюза): адаптация и агрегация под нужды клиента.
- **Service Mesh** — *сеть между сервисами* (внутри): устойчивость, mTLS, наблюдаемость межсервисного трафика.

Gateway/BFF — на *границе* (север-юг трафик, клиент↔система); Mesh — *между сервисами* (восток-запад трафик, сервис↔сервис). Это дополняющие, не конкурирующие паттерны: типичная система имеет и шлюз на входе, и mesh внутри.

### 2.5. Операционная цена и «по нужде»

Все три несут операционную цену (эхо 5.2, 6.3): шлюз — единая точка (надо делать отказоустойчивой, не дать стать горлышком); BFF — больше API поддерживать (по одному на клиента); mesh — серьёзная инфраструктура (сайдкары, control plane, эксплуатация — Модуль 9). Поэтому — *по нужде*:
- **Gateway** окупается, когда сервисов несколько и нужны общие пограничные заботы; для одного сервиса избыточен.
- **BFF** — когда клиенты *реально* расходятся в нуждах; не «BFF на каждый каприз».
- **Service Mesh** — когда сервисов *много* и сквозные сетевые заботы (устойчивость, mTLS, трейсинг) стали болью вписывать в каждый; для трёх сервисов mesh — тяжёлый over-engineering (как преждевременные микросервисы 2.3, полиглот 5.2). Часто проще библиотека устойчивости (4.4) в коде, чем mesh.

### 2.6. Связь с пройденным

Эти паттерны выносят на инфраструктуру то, что мы изучали как код/решения: устойчивость (4.4) → mesh; маршрутизация/фильтры/агрегация (EIP 5.6) → gateway; адаптация под клиента (6.2 GraphQL/агрегация) → BFF; безопасность на входе и mTLS (Модуль 7) → gateway/mesh; наблюдаемость (Модуль 8) → mesh; деплой canary (Модуль 9) → mesh. Они — инфраструктурное воплощение сквозных забот, и закрывают Модуль 6, связывая взаимодействие с эксплуатацией (Модуль 9) и безопасностью (Модуль 7).

## 3. Подходы

**Подход 1.** API Gateway — для сквозных *пограничных* задач (маршрутизация, аутентификация, rate limiting, TLS) при нескольких сервисах; держи его *тонким* — без бизнес-логики (2.1).

**Подход 2.** BFF — когда клиенты реально расходятся в нуждах: свой API на тип клиента, заточенный и развиваемый его командой; адаптация/агрегация, не бизнес-логика (2.2). Не плоди BFF без нужды.

**Подход 3.** Service Mesh — когда сервисов много и сквозные сетевые заботы (устойчивость 4.4, mTLS, трейсинг) стали болью; выносит их на инфраструктуру единообразно (2.3). Для немногих сервисов — библиотека устойчивости в коде проще (2.5).

**Подход 4.** Не путай задачи: Gateway/BFF на границе (клиент↔система), Mesh между сервисами (сервис↔сервис) — дополняют друг друга (2.4).

**Подход 5.** Не раздувай Gateway/BFF в god-компонент с бизнес-логикой (повтор ESB/умной трубы, 2.3, 5.6) — тонкий слой, логика в сервисах (2.1, 2.2).

**Подход 6.** Считай операционную цену, применяй по нужде: каждый паттерн зарабатывает место (2.5, как полиглот 5.2); единую точку (gateway) делай отказоустойчивой.

**Подход 7.** Связывай с безопасностью (Модуль 7: аутентификация на gateway, mTLS на mesh), наблюдаемостью (Модуль 8: трейсинг на mesh), деплоем (Модуль 9: canary на mesh) — это их естественная роль (2.6).

## 4. Пример кода: роли (концептуально)

```typescript
// API GATEWAY: тонкая граница — маршрутизация + сквозные пограничные заботы (2.1).
// БЕЗ бизнес-логики (подход 5).
class ApiGateway {
  async handle(req: Request): Promise<Response> {
    if (!(await this.auth.verify(req))) return Response.unauthorized(); // аутентификация (Модуль 7)
    if (!this.rateLimiter.allow(req.clientId)) return Response.tooManyRequests(); // rate limiting
    const service = this.router.routeFor(req.path); // маршрутизация к сервису (EIP, 5.6)
    return this.forward(service, req); // проксируем — НЕ исполняем бизнес-логику
  }
}

// BFF: API под КОНКРЕТНОГО клиента — агрегация под его экраны, заточенный ответ (2.2).
class MobileBFF {
  // Мобильному нужен компактный набор под экран заказа — агрегируем из нескольких сервисов.
  async orderScreen(orderId: string): Promise<MobileOrderView> {
    const [order, tracking] = await Promise.all([
      this.orders.get(orderId), // внутренние сервисы (по gRPC, 6.2)
      this.delivery.tracking(orderId),
    ]);
    // Отдаём ТОЛЬКО нужное мобильному (компактно) — не общий "толстый" ответ (6.2, over-fetching).
    return { id: order.id, total: order.total, status: tracking.status };
  }
}

// SERVICE MESH: конфигурация (декларативно, НЕ в коде сервиса). Устойчивость (4.4) на инфраструктуре.
const meshConfig = {
  service: "inventory",
  timeout: "500ms", // таймаут (4.4) — на mesh, не в коде каждого вызывающего
  retries: { attempts: 2, backoff: "exponential" }, // повтор с backoff (4.4)
  circuitBreaker: { errorThreshold: "50%", interval: "10s" }, // размыкатель (4.4)
  mtls: true, // шифрование+аутентификация между сервисами (zero trust, Модуль 7)
  tracing: true, // распределённый трейсинг (Модуль 8)
};
```

**Суть:** Gateway — тонкая граница (маршрутизация, auth, rate limiting), без бизнес-логики. BFF — заточенная агрегация под конкретного клиента (компактный мобильный ответ из нескольких сервисов). Mesh — устойчивость (4.4: таймаут/повтор/размыкатель), mTLS и трейсинг *декларативно на инфраструктуре*, а не в коде каждого сервиса. Три разные роли (2.4): граница для клиентов (gateway/BFF) и сеть между сервисами (mesh).

## 5. Развёрнутый кейс: граница и сеть платформы

Платформа из многих сервисов с разными клиентами выстраивает взаимодействие.

**API Gateway на входе.** Раньше каждый сервис сам делал аутентификацию, rate limiting, TLS — дублирование, несогласованность, клиенту надо знать все адреса. Поставили **шлюз** (2.1): единая точка входа, централизованные аутентификация (Модуль 7), rate limiting, маршрутизация, TLS-терминация. Сервисы освободились от пограничных забот. Держат шлюз *тонким* (подход 5) — бизнес-логику не пускают, чтобы не повторить ESB (2.3, 5.6).

**BFF под клиентов.** Мобильное и веб-приложение расходились в нуждах (6.2): мобильному — компактно (трафик), вебу — богато. Один общий API всех не устраивал (over/under-fetching). Сделали **BFF на клиента** (2.2): мобильный BFF (компактные агрегированные ответы) и веб BFF (богатые), каждый развивается командой клиента, агрегирует из внутренних сервисов (по gRPC, 6.2). Не стали плодить BFF сверх двух реальных клиентов (подход 2).

**Service Mesh внутри.** Сервисов стало много, и сквозные сетевые заботы — устойчивость (таймауты, повторы, circuit breaker — 4.4), mTLS, трейсинг — приходилось вписывать в *каждый* сервис на разных языках (дублирование). Внедрили **mesh** (2.3): эти заботы ушли в сайдкары, декларативно и единообразно, вне кода сервисов. Устойчивость из 4.4 стала свойством платформы; mTLS дал zero trust (Модуль 7); трейсинг — наблюдаемость межсервисного трафика (Модуль 8).

**Ошибки.** Команда А раздула шлюз бизнес-логикой (трансформации, оркестрация процессов) — он стал god-компонентом и узким горлышком (повтор ESB, 2.3, 5.6); вернули логику в сервисы, шлюз — тонкий. Команда Б (3 сервиса, маленькая) внедрила полноценный service mesh «как у больших» — утонула в эксплуатации control plane и сайдкаров при отсутствии выгод (преждевременный mesh, 2.5); откатилась на простую библиотеку устойчивости (4.4) в коде, которой для трёх сервисов хватало.

**Мораль:** три паттерна — три задачи: gateway (пограничные заботы, тонкий), BFF (адаптация под клиента, по нужде), mesh (межсервисные сетевые заботы, когда сервисов много). Не раздувать (god-gateway), не плодить (BFF), не тащить преждевременно (mesh для трёх сервисов) — каждый по нужде и в своей роли, как и всё в учебнике.

## 6. Антипаттерны и ловушки

**God-Gateway.** Бизнес-логика, трансформации, оркестрация в шлюзе (кейс): узкое горлышко и ком грязи, повтор ESB/умной трубы (2.3, 5.6). Шлюз тонкий — только пограничные сквозные заботы.

**BFF на каждый каприз.** Плодить BFF без реального расхождения клиентов (2.2): много API поддерживать без выгоды. BFF — где клиенты реально различны.

**Преждевременный Service Mesh.** Внедрять mesh в систему из немногих сервисов «как у больших» (кейс, 2.5): тяжёлая инфраструктура (control plane, сайдкары) без выгод. Для немногих — библиотека устойчивости (4.4) в коде проще.

**Путаница ролей.** Использовать gateway для межсервисной устойчивости или mesh для пограничной аутентификации клиентов (2.4): gateway/BFF — граница, mesh — между сервисами. Не смешивай.

**Gateway как единая точка отказа.** Не сделать шлюз отказоустойчивым (2.5): он лежит — лежит вход во всю систему. Резервируй.

**Бизнес-логика в BFF.** BFF делает бизнес-решения вместо адаптации/агрегации (2.2): дублирует логику сервисов, расходится с ними. BFF — тонкая адаптация, логика в сервисах.

**Mesh не отменяет понимания устойчивости.** Думать, что mesh «сам всё сделает»: ты всё равно настраиваешь таймауты/повторы/размыкатели (4.4) осознанно (наивный retry в mesh = retry storm 4.4). Mesh — инструмент, не магия.

## 7. Ключевые выводы (чеклист)

- [ ] **API Gateway** — единая точка входа для клиентов: маршрутизация, аутентификация, rate limiting, TLS на границе. **Тонкий**, без бизнес-логики (иначе god-компонент/ESB).
- [ ] **BFF** — API под *конкретного клиента* (мобильный/веб): адаптация и агрегация под его нужды; не бизнес-логика; по нужде, не на каждый каприз.
- [ ] **Service Mesh** — управление сетью *между сервисами*: устойчивость (4.4), mTLS, наблюдаемость, маршрутизация — на инфраструктуре (сайдкары), вне кода.
- [ ] **Три разные задачи:** Gateway/BFF на **границе** (клиент↔система), Mesh **между сервисами** — дополняют, не путать.
- [ ] Все три несут **операционную цену** — применяй **по нужде**: gateway при нескольких сервисах, BFF при реальном расхождении клиентов, mesh при многих сервисах (для немногих — библиотека устойчивости).
- [ ] Они **выносят на инфраструктуру** сквозные заботы, изученные как код: устойчивость (4.4), безопасность (Модуль 7), наблюдаемость (Модуль 8), деплой (Модуль 9).
- [ ] **Не раздувай** (god-gateway/BFF), **не плоди** (BFF), **не тащи преждевременно** (mesh) — каждый в своей роли и по нужде.

2. Почему Gateway/BFF надо держать тонкими? Какой антипаттерн повторяется при раздувании шлюза бизнес-логикой?

4. Есть ли в твоей системе шлюз? Тонкий ли он или в нём бизнес-логика? Как сервисы решают аутентификацию/rate limiting — централизованно или каждый сам?
5. Как у вас реализована устойчивость между сервисами (4.4) — в коде каждого сервиса или на инфраструктуре (mesh)? Есть ли дублирование? Оправдан ли mesh по числу сервисов?
6. Возьми код-пример из раздела 4: добавь веб-BFF (богаче мобильного) для того же экрана заказа и покажи, чем его ответ отличается. Почему это лучше одного общего API (6.2)?
