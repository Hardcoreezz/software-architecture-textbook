# Глава 6.5. API Gateway, BFF, Service Mesh

> Модуль 6. Взаимодействие сервисов и API
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

Когда система — это много сервисов, которые общаются через API и брокеры ([6.1](06-01-sinhronnoe-vs-asinhronnoe.md)–[6.4](06-04-proektirovanie-api-versionirovanie.md)), появляются сквозные задачи на границе и в сети между сервисами. Клиентам нужна единая точка входа с аутентификацией, маршрутизацией и ограничением частоты, а ещё способ получить данные экрана без вызовов десяти сервисов. Между сервисами нужны таймауты, повторы, mTLS и трейсинг, и вписывать их в каждый сервис дорого. Эти задачи решают три инфраструктурных паттерна: **API Gateway** (единая точка входа), **BFF** (API под конкретного клиента) и **Service Mesh** (управление взаимодействием между сервисами).

Их часто путают и применяют не к месту: шлюз раздувают до god-компонента с бизнес-логикой, BFF плодят без нужды, mesh тащат в систему из трёх сервисов. У каждого своя задача и своя операционная цена, поэтому применяй их по нужде, а не по моде.

---

## 2. Теория

### 2.1. API Gateway: единая точка входа

**API Gateway** — единая точка входа для внешних клиентов перед набором сервисов. Клиент обращается к шлюзу, шлюз направляет запрос нужному сервису и берёт на себя сквозные пограничные задачи:

- маршрутизация запросов к сервисам;
- аутентификация и авторизация на входе ([Модуль 7](../07-bezopasnost/README.md));
- ограничение частоты (rate limiting) и квоты;
- TLS-терминация и агрегация ответов нескольких сервисов;
- кэширование на границе ([5.4](../05-dannye/05-04-strategii-keshirovaniya.md)), логирование, метрики входа.

Без шлюза каждый сервис сам реализует аутентификацию, rate limiting и TLS — с дублированием и расхождениями, а клиент должен знать адреса всех сервисов. В терминах EIP ([5.6](../05-dannye/05-06-patterny-integracii-eip.md)) шлюз — это Content-Based Router со сквозными фильтрами на границе.

**Граница ответственности:** шлюз решает сквозные пограничные задачи, но не исполняет бизнес-логику. Если бизнес-логика затекает в шлюз, он становится god-компонентом и узким горлышком — это повтор ошибки ESB, «умной трубы» из SOA ([2.3](../02-stili/02-03-mikroservisy-i-soa.md)).

### 2.2. BFF: Backend for Frontend

**BFF** (Backend for Frontend) — отдельный API-слой под конкретный тип клиента: мобильный, веб, партнёрский. Один общий REST-API — компромисс: пытаясь угодить всем клиентам, он переусложняется, и всё равно одним приходит лишнее, а другим не хватает данных (over/under-fetching, [6.2](06-02-rest-grpc-graphql.md)). С BFF у каждого клиента свой API: мобильный отдаёт компактные ответы, веб — богатые, и каждый агрегирует данные внутренних сервисов под конкретные экраны.

Развивает BFF команда того клиента, которому он служит. Наружу его часто делают на GraphQL или агрегирующем REST, а внутренние сервисы он зовёт по gRPC.

**Граница:** BFF отвечает за адаптацию под клиента и агрегацию, а бизнес-логика остаётся в сервисах.

### 2.3. Service Mesh: управление межсервисной сетью

**Service Mesh** (сервисная сетка) — инфраструктурный слой, который управляет взаимодействием между сервисами внутри системы, а не на границе с клиентом. Он работает через прокси, перехватывающие межсервисный трафик. Классически это сайдкар (sidecar) рядом с каждым сервисом; бывают и режимы без сайдкаров, с общими прокси. Mesh берёт на себя сетевые заботы, которые иначе пришлось бы вписывать в каждый сервис:

- устойчивость: таймауты, повторы, circuit breaker ([4.4](../04-raspredelennye-sistemy/04-04-patterny-ustoychivosti.md));
- mTLS — шифрование и взаимная аутентификация между сервисами ([7.3](../07-bezopasnost/07-03-zero-trust.md));
- service discovery, балансировка, маршрутизация (canary, A/B);
- наблюдаемость: распределённый трейсинг и метрики межсервисного трафика ([Модуль 8](../08-nadezhnost-nablyudaemost-proizvoditelnost/README.md)).

Эти заботы одинаковы для всех сервисов, и писать их в каждом сервисе на каждом языке — дублирование. Mesh даёт их единообразно и декларативно: таймауты, повторы и размыкатели, которые в 4.4 кодировали вручную, становятся настройкой платформы. Две оговорки. Деградация и fallback остаются в коде: это семантика приложения. С трейсингом mesh тоже справляется не целиком: прокси записывают участки трассы (спаны), но заголовки трассировки сервис пробрасывает сам (обычно через OpenTelemetry).

### 2.4. Три разные задачи — не путать

API Gateway и BFF работают на границе с внешними клиентами — это трафик «север-юг» (клиент ↔ система); BFF часто стоит за шлюзом или входит в него. Service Mesh работает между сервисами — это трафик «восток-запад» (сервис ↔ сервис). Паттерны дополняют друг друга, а не конкурируют: крупная микросервисная система часто имеет и шлюз на входе, и mesh внутри.

### 2.5. Операционная цена и «по нужде»

Все три паттерна несут операционную цену. Шлюз — единая точка входа: его надо делать отказоустойчивым и не дать ему стать узким горлышком. BFF — ещё один API на поддержке для каждого клиента. Mesh — серьёзная инфраструктура: прокси, control plane, эксплуатация ([Модуль 9](../09-cloud-native-infrastruktura-dostavka/README.md)). Поэтому каждый вводят, только когда он окупается: для трёх сервисов mesh — тяжёлый over-engineering, как преждевременные микросервисы ([2.3](../02-stili/02-03-mikroservisy-i-soa.md)).

## 3. Подходы

**Подход 1.** Ставь API Gateway, когда сервисов несколько и им нужны общие пограничные задачи; для одного сервиса он избыточен. Держи шлюз тонким, без бизнес-логики.

**Подход 2.** Заводи BFF на тип клиента, только когда клиенты реально расходятся в нуждах, а не «BFF на каждый каприз». Отдавай его команде этого клиента.

**Подход 3.** Начинай межсервисную устойчивость с библиотеки в коде. Переходи на Service Mesh, когда сервисов много и вписывать устойчивость, mTLS и трейсинг в каждый стало больно.

**Подход 4.** Раскладывай задачи по местам: аутентификацию клиентов и rate limiting — на gateway; mTLS, межсервисную устойчивость, трейсинг и canary-маршрутизацию ([9.4](../09-cloud-native-infrastruktura-dostavka/09-04-ci-cd-deployment-strategii.md)) — в mesh.

## 4. Пример кода: роли (концептуально)

```typescript
// API GATEWAY: тонкая граница — только сквозные пограничные задачи (§2.1).
interface Auth { verify(req: Request): Promise<{ clientId: string } | null>; } // личность клиента или null
interface RateLimiter { allow(clientId: string): boolean; }
interface Router { routeFor(url: URL): URL; } // адрес сервиса по URL запроса (путь и query)

class ApiGateway {
  constructor(private auth: Auth, private rateLimiter: RateLimiter, private router: Router) {}

  async handle(req: Request): Promise<Response> {
    const identity = await this.auth.verify(req); // аутентификация
    if (!identity) return new Response(null, { status: 401 });
    // rate limiting — по проверенной личности, а не по заголовку, который клиент может подменить
    if (!this.rateLimiter.allow(identity.clientId)) return new Response(null, { status: 429 });
    const target = this.router.routeFor(new URL(req.url)); // маршрутизация
    return fetch(new Request(target, req)); // проксируем как есть — бизнес-логики здесь нет
  }
}

// BFF: API под конкретного клиента — агрегация под его экран (§2.2).
interface OrdersClient { get(id: string): Promise<{ id: string; total: number; items: string[] }>; }
interface DeliveryClient { tracking(orderId: string): Promise<{ status: string; route: string[] }>; }
interface MobileOrderView { id: string; total: number; status: string; }

class MobileBFF {
  constructor(private orders: OrdersClient, private delivery: DeliveryClient) {} // клиенты внутренних сервисов (gRPC)

  async orderScreen(orderId: string): Promise<MobileOrderView> {
    const [order, tracking] = await Promise.all([
      this.orders.get(orderId),
      this.delivery.tracking(orderId),
    ]);
    // Мобильному — только поля экрана, а не общий «толстый» ответ (over-fetching, 6.2).
    return { id: order.id, total: order.total, status: tracking.status };
  }
}

// SERVICE MESH: декларативная конфигурация платформы, а не код сервиса (§2.3).
const meshConfig = {
  service: "inventory",
  timeout: "500ms", // таймаут (4.4) — не в коде каждого вызывающего
  retries: { attempts: 2, backoff: "exponential" }, // повтор с backoff (4.4)
  circuitBreaker: { errorThreshold: "50%", interval: "10s" }, // размыкатель (4.4)
  mtls: true, // взаимная аутентификация и шифрование между сервисами (Модуль 7)
  tracing: true, // распределённый трейсинг (оговорка — в §2.3)
};
```

**Суть:** шлюз не знает, что такое заказ, а BFF знает экран мобильного клиента, но не правила домена — их по-прежнему исполняют сервисы.

## 5. Развёрнутый кейс: граница и сеть платформы

Платформа из многих сервисов с мобильным и веб-клиентом выстраивает взаимодействие.

**API Gateway на входе.** Раньше каждый сервис сам делал аутентификацию, rate limiting и TLS. Поставили шлюз и централизовали на нём аутентификацию ([Модуль 7](../07-bezopasnost/README.md)), rate limiting, маршрутизацию и TLS-терминацию. Сервисы освободились от пограничных забот.

**BFF под клиентов.** Мобильному нужны компактные ответы, чтобы экономить трафик, вебу — богатые, и один общий REST-API не устраивал ни тех, ни других. Сделали два BFF — мобильный и веб. В кейсе [6.2](06-02-rest-grpc-graphql.md) ту же задачу решил один GraphQL-слой; здесь выбрали BFF, чтобы API каждого клиента развивала его собственная команда. Оба BFF агрегируют данные внутренних сервисов по gRPC. Третий BFF заводить не стали: реальных клиентов два.

**Service Mesh внутри.** Сервисов стало много, и таймауты, повторы, circuit breaker ([4.4](../04-raspredelennye-sistemy/04-04-patterny-ustoychivosti.md)), mTLS и трейсинг приходилось вписывать в каждый сервис на разных языках. Внедрили mesh: устойчивость стала свойством платформы, mTLS дал основу zero trust ([7.3](../07-bezopasnost/07-03-zero-trust.md)), а трейсинг — наблюдаемость межсервисного трафика.

**Ошибка.** Соседняя команда с системой из трёх сервисов внедрила полноценный mesh «как у больших», утонула в эксплуатации control plane и сайдкаров без всякой выгоды и откатилась на библиотеку устойчивости в коде — для трёх сервисов её хватало.

## 6. Антипаттерны и ловушки

**God-Gateway.** В шлюз затекают бизнес-правила, оркестрация процессов и доменные преобразования данных. Он становится узким горлышком и комом грязи в центре системы (§2.1).

**Gateway как единая точка отказа.** Шлюз не зарезервирован: упал он — недоступен вход во всю систему.

**Бизнес-логика в BFF.** BFF принимает бизнес-решения вместо адаптации и агрегации. Он дублирует логику сервисов и со временем расходится с ней.

**Преждевременный Service Mesh.** Mesh внедряют в систему из немногих сервисов «как у больших» (соседняя команда в кейсе) и платят за эксплуатацию control plane и прокси без всякой выгоды.

**Путаница ролей.** Межсервисную устойчивость решают на шлюзе либо переносят в mesh аутентификацию внешних клиентов (см. §2.4).

**Mesh не отменяет понимания устойчивости.** Mesh не «сделает всё сам»: таймауты, повторы и размыкатели ты всё равно настраиваешь осознанно. Наивные повторы в mesh дают тот же retry storm ([4.4](../04-raspredelennye-sistemy/04-04-patterny-ustoychivosti.md)). Mesh — инструмент, а не магия.

## 7. Ключевые выводы (чеклист)

- [ ] **API Gateway** — единая точка входа: маршрутизация, аутентификация, rate limiting, TLS. **Тонкий**, без бизнес-логики, зарезервированный.
- [ ] **BFF** — API под конкретного клиента: адаптация и агрегация без бизнес-логики.
- [ ] **Service Mesh** — сеть между сервисами: таймауты, повторы, размыкатели, mTLS, маршрутизация и наблюдаемость в прокси. Деградация и проброс заголовков трассировки остаются в коде.
- [ ] Gateway и BFF — на **границе** (север-юг), mesh — **между сервисами** (восток-запад). Они дополняют друг друга.
- [ ] Все три несут **операционную цену**, поэтому вводи их по нужде: gateway — при нескольких сервисах, BFF — при реальном расхождении клиентов, mesh — при многих сервисах (для немногих — библиотека устойчивости).

## 8. Упражнения и вопросы

1. Чем различаются задачи Gateway, BFF и Service Mesh? Какие из них работают на границе, какой — между сервисами, и почему они дополняют друг друга?
2. Почему Gateway и BFF держат тонкими? Какую ошибку SOA повторяет шлюз с бизнес-логикой?
3. Когда service mesh окупается, а когда это over-engineering? Что взять вместо него для немногих сервисов?
4. Есть ли в твоей системе шлюз и нет ли в нём бизнес-логики? Как сервисы решают аутентификацию и rate limiting — централизованно или каждый сам?
5. Где у вас живёт межсервисная устойчивость ([4.4](../04-raspredelennye-sistemy/04-04-patterny-ustoychivosti.md)) — в коде каждого сервиса или в mesh? Есть ли дублирование, оправдан ли mesh числом сервисов?
6. Добавь в пример из §4 веб-BFF для того же экрана заказа (богаче мобильного) и покажи, чем отличается его ответ. Почему это лучше одного общего REST-API ([6.2](06-02-rest-grpc-graphql.md))?
7. Спроектируй пограничную и межсервисную инфраструктуру для системы по выбору: нужен ли gateway и что на нём, сколько BFF и под каких клиентов, нужен ли mesh. Обоснуй каждое решение нуждой.
