# Глава 6.2. REST, gRPC, GraphQL

> Модуль 6. Взаимодействие сервисов и API
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

[Глава 6.1](06-01-sinhronnoe-vs-asinhronnoe.md) задала ось синхронно/асинхронно. Когда взаимодействие *синхронное* (request-response), встаёт следующий вопрос: *каким стилем* API? Три доминирующих ответа — **REST, gRPC, GraphQL**. И, как с архитектурными стилями ([Модуль 2](../02-stili/README.md)) и хранилищами ([5.1](../05-dannye/05-01-vybor-hranilisch.md)), их часто выбирают по моде или привычке: «REST, потому что все так», «GraphQL, потому что современно», «gRPC, потому что быстро». Это ведёт к решениям не по делу: GraphQL в простой внутренний CRUD (лишняя сложность), gRPC в публичный браузерный API (нельзя вызвать из браузера), REST там, где нужна производительность и стриминг.

Эта глава даёт три стиля честно: модель каждого, сильные стороны, компромиссы и — главное — *когда какой уместен*. Это прямое продолжение метода всего учебника: нет «лучшего» стиля API, есть подходящий контексту (эхо [2.7](../02-stili/02-07-kak-vybirat-stil.md)), и выбор диктуют *кто клиент*, *форма данных* и *требования* (производительность, контракт, кэширование), а не мода. И ключевое: **они сосуществуют** — gRPC между сервисами внутри, REST/GraphQL на границе для клиентов, — это не «выбери один на всё» (как гибрид стилей в и парадигм в [5.5](../05-dannye/05-05-batch-stream-konveery.md)).

Главная установка: **REST, gRPC, GraphQL — не конкуренты, где один побеждает, а инструменты под разные контексты API**; выбирай по клиенту и форме данных, и не бойся комбинировать. Все три — обычно синхронны ([6.1](06-01-sinhronnoe-vs-asinhronnoe.md)); асинхронный эквивалент — обмен сообщениями ([6.3](06-03-ocheredi-brokery-streaming-kafka.md)).

## 2. Теория

### 2.1. REST

**REST (Representational State Transfer)** — ресурс-ориентированный стиль поверх HTTP: *ресурсы* адресуются URL (`/orders/123`), действия выражаются *HTTP-глаголами* (GET/POST/PUT/DELETE), используется семантика HTTP (коды статусов, кэширование), взаимодействие *stateless*.

*Сильные стороны:* **повсеместность и простота** (понятен всем, огромная экосистема инструментов); **использует HTTP** (кэширование на уровне HTTP — связь с [5.4](../05-dannye/05-04-strategii-keshirovaniya.md), прокси, CDN); **слабая связанность** (нет жёсткого бинарного контракта); **человекочитаемость** (JSON, легко отлаживать); идеален для **публичных API и CRUD**.

*Слабые стороны:* **over/under-fetching** — ответ фиксирован, получаешь *лишнее* (over) или нужно *несколько запросов* за связанными данными (under); **болтливость** за связанными данными ([3.5](../03-dekompoziciya-ddd/03-05-granicy-servisov-i-moduley.md), [4.1](../04-raspredelennye-sistemy/04-01-zabluzhdeniya-i-setevye-osnovy.md)); **слабый контракт по умолчанию** (хотя OpenAPI/спецификации помогают); не идеален для RPC-стиля и стриминга.

### 2.2. gRPC

**gRPC** — contract-first RPC поверх HTTP/2: контракт описан в схеме (Protocol Buffers), передача *бинарная*, вызов в *RPC-стиле* (зовёшь методы как функции), поддержка *стриминга* (в т.ч. двунаправленного), генерация кода из схемы.

*Сильные стороны:* **производительность** (бинарный формат, HTTP/2, мультиплексирование); **строгий типизированный контракт** (protobuf — генерируется код, проверяется типами); **стриминг** (потоковые вызовы); идеален для **внутреннего взаимодействия сервис-сервис**, высокой пропускной способности, полиглотных внутренних систем.

*Слабые стороны:* **бинарность** (не человекочитаем, труднее отлаживать «на глаз»); **ограниченная поддержка в браузере** (нужен прокси gRPC-Web); более сложная оснастка; **не для публичных/веб-API** обычно; **RPC-связанность** (метод-ориентированность — теснее, чем ресурсная).

### 2.3. GraphQL

**GraphQL** — язык запросов к API: клиент указывает *точно, какие данные* ему нужны (один запрос, без over/under-fetching), строго типизированная *схема*, обычно *единая конечная точка*.

*Сильные стороны:* **клиент контролирует ответ** (решает over/under-fetching — берёт ровно нужные поля); **один запрос за сложными/вложенными данными** (заказ + позиции + клиент разом); **строгая схема и интроспекция**; идеален для **разнородных клиентов** (мобильный и веб с *разными* потребностями в данных), сложных вложенных данных, **агрегации нескольких источников**.

*Слабые стороны:* **сложность сервера** (резолверы, проблема **N+1 запросов**); **кэширование труднее** (единый endpoint, обычно POST — не ложится на HTTP-кэш [5.4](../05-dannye/05-04-strategii-keshirovaniya.md)); **производительные ловушки** (произвольные запросы клиента → дорогие операции); **безопасность** (атаки глубиной/сложностью запроса — DoS); **избыточен для простых API**.

### 2.4. Это не конкуренты — это инструменты под контекст

Главная мысль (эхо [5.1](../05-dannye/05-01-vybor-hranilisch.md)): эти три — *не* соперники, где один «лучший». Каждый подходит своему контексту. Выбор диктуют:
- **Кто клиент?** Браузер/веб; мобильный; внутренний сервис; публичный/сторонний; разнородные клиенты с разными нуждами.
- **Форма данных?** Простой CRUD; вложенный граф; потоки (стриминг).
- **Требования?** Производительность; строгость контракта; кэширование; человекочитаемость.

Сводно, *когда что* (запахи, как в §2.5):
- **REST** — публичные API, CRUD, веб, когда важны HTTP-кэширование/повсеместность/простота.
- **gRPC** — внутреннее сервис-сервис, высокая производительность, стриминг, полиглот внутри, строгий контракт.
- **GraphQL** — разнородные клиенты с разными нуждами в данных, сложные вложенные данные, агрегация источников, клиент-driven выборка.

### 2.5. Они сосуществуют

Очень частый и правильный паттерн (эхо гибрида из [5.5](../05-dannye/05-05-batch-stream-konveery.md)): **gRPC между сервисами внутри** (производительность, контракт) + **REST или GraphQL на границе** для внешних клиентов (повсеместность/клиент-driven). Внешний клиент бьёт в GraphQL/REST шлюз, а тот общается с внутренними сервисами по gRPC. Это не «выбери один на всё», а слои с разными стилями под разные контексты (мост к API Gateway/BFF [6.5](06-05-api-gateway-bff-service-mesh.md)).

### 2.6. Контракт и связанность

Стили различаются *строгостью контракта*, и это компромисс ([0.4](../00-professiya/00-04-arhitekturnoe-myshlenie.md)):
- **gRPC/GraphQL** — строгий типизированный контракт (protobuf-схема / GraphQL-схема): генерация кода, проверка типами, безопаснее, лучше оснастка — но *теснее связь* со схемой (изменение схемы задевает клиентов; мост к версионированию [6.4](06-04-proektirovanie-api-versionirovanie.md)).
- **REST** — полагается на соглашения + OpenAPI: слабее по умолчанию, но *гибче* (легче эволюционировать без жёсткой схемы).

Строгий контракт = безопасность и оснастка ценой связанности; слабый = гибкость ценой безопасности. Как всегда — компромисс под контекст; и эволюция контракта (версионирование) — отдельная важная тема.

## 3. Подходы

**Подход 1. Выбирай по клиенту и форме данных.** Кто клиент (браузер/мобильный/внутренний сервис/публичный)? Какая форма (CRUD/граф/стриминг)? Какие требования (производительность/кэш/контракт)? Это диктует стиль (§2.4), а не мода.

**Подход 2. REST — для публичного/CRUD/веб с кэшированием.** Повсеместность, простота, HTTP-кэш ([5.4](../05-dannye/05-04-strategii-keshirovaniya.md)), человекочитаемость — REST силён для публичных API, простого CRUD, веба (§2.1).

**Подход 3. gRPC — для внутреннего высокопроизводительного/стриминга.** Сервис-сервис внутри, высокая пропускная способность, стриминг, полиглот, строгий контракт — gRPC (§2.2). Не для браузера/публичного без необходимости.

**Подход 4. GraphQL — для разнородных клиентов и вложенных данных.** Клиенты с разными нуждами (мобильный/веб), сложные вложенные данные, агрегация источников, клиент-driven выборка — GraphQL (§2.3). Не для простого CRUD (избыточен).

**Подход 5. Комбинируй слоями.** gRPC внутри + REST/GraphQL на границе (§2.5) — норма, не «один на всё». Разные стили под разные контексты, как гибрид в [2.7](../02-stili/02-07-kak-vybirat-stil.md).

**Подход 6. Учитывай ловушки GraphQL.** N+1 (dataloader/батчинг), ограничения глубины/сложности запроса (от DoS), сложность резолверов, трудность кэширования. Не бери GraphQL, не приняв этой цены.

**Подход 7. Учитывай ограничения gRPC.** Браузер (нужен gRPC-Web/прокси), человекочитаемость (бинарь), оснастка. Не для публичного браузерного API без необходимости.

**Подход 8. Помни про контракт/связанность и версионирование.** Строгий контракт (gRPC/GraphQL) безопасен, но связывает со схемой (§2.6); эволюцию планируй (версионирование, [6.4](06-04-proektirovanie-api-versionirovanie.md)). REST гибче, но требует дисциплины (OpenAPI).

## 4. Пример кода: одна операция — три стиля

Покажем over/under-fetching и контракт на TypeScript: получить заказ с позициями и данными клиента. Сначала — REST.

```typescript
// REST: ресурсы и HTTP-глаголы. Проблема over/under-fetching (§2.1).
// Вариант A — под-выборка: НЕСКОЛЬКО запросов за связанными данными (болтливость, 3.5).
const order = await fetch(`/orders/123`).then((r) => r.json()); // заказ
const lines = await fetch(`/orders/123/lines`).then((r) => r.json()); // ещё запрос за позициями
const customer = await fetch(`/customers/${order.customerId}`).then((r) => r.json()); // ещё за клиентом
// 3 запроса (under-fetching) ИЛИ один "толстый" эндпоинт, отдающий ВСЁ всегда (over-fetching).
// Плюсы REST: HTTP-кэш (5.4) для GET, повсеместность, человекочитаемость, простота.
```

Теперь — gRPC: типизированный RPC-вызов по бинарному контракту.

```protobuf
// Контракт gRPC (Protocol Buffers): строгая схема, из неё генерируется код (§2.2, §2.6).
service OrderService {
  rpc GetOrder(GetOrderRequest) returns (OrderReply); // RPC-метод, как вызов функции
}
message GetOrderRequest { string order_id = 1; }
message OrderReply {
  string order_id = 1;
  repeated OrderLine lines = 2; // вложенные данные в одном бинарном ответе
  Customer customer = 3;
}
```

```typescript
// Вызов gRPC (по сгенерированному из схемы клиенту): типизированный RPC, бинарно, HTTP/2.
const reply = await orderClient.getOrder({ orderId: "123" }); // ОДИН быстрый бинарный вызов
// Плюсы: производительность, строгий контракт (типы из protobuf), стриминг.
// Минусы: не из браузера напрямую, бинарь (не почитать глазами), связь со схемой (§2.6).
```

И — GraphQL: клиент указывает *точно* нужные поля одним запросом.

```typescript
// GraphQL: КЛИЕНТ выбирает ровно нужные поля — нет over/under-fetching, ОДИН запрос (§2.3).
const query = `
  query {
    order(id: "123") {
      id
      lines { sku qty }        # берём только нужные поля позиций
      customer { name }        # и только имя клиента — не весь объект (нет over-fetching)
    }
  }`;
const data = await fetch(`/graphql`, { method: "POST", body: JSON.stringify({ query }) })
  .then((r) => r.json());
// Плюсы: клиент контролирует ответ, один запрос за вложенным графом, строгая схема.
// Минусы: N+1 на резолверах (§2.3), кэш труднее (POST, единый endpoint), риск дорогих запросов.
```

**Что показывает пример.** Одна операция (заказ + позиции + клиент), три стиля с разными компромиссами. **REST** прост и человекочитаем, использует HTTP-кэш ([5.4](../05-dannye/05-04-strategii-keshirovaniya.md)) — но страдает от over/under-fetching: либо три запроса (болтливость, [3.5](../03-dekompoziciya-ddd/03-05-granicy-servisov-i-moduley.md)), либо «толстый» эндпоинт, отдающий лишнее. **gRPC** даёт *один быстрый бинарный* вызов с *строгим контрактом* (protobuf, типы) — идеален внутри между сервисами, но не из браузера и не почитать глазами (§2.2). **GraphQL** позволяет *клиенту* выбрать ровно нужные поля одним запросом (решает over/under-fetching, §2.3) — идеален для разнородных клиентов, но несёт N+1, сложность резолверов и трудность кэширования. Заметь: «лучшего» среди них *нет* (§2.4) — REST для публичного/кэшируемого, gRPC для внутреннего быстрого, GraphQL для клиент-driven вложенного. И они *сосуществуют* (§2.5): этот GraphQL/REST на границе вполне может внутри звать `OrderService` по gRPC.

## 5. Развёрнутый кейс: API-стили платформы по контексту

Платформа имеет несколько типов клиентов и взаимодействий. Подберём стиль *под контекст каждого* — и придём к сосуществованию (§2.5), а не к одному стилю на всё.

**Внутреннее сервис-сервис → gRPC.** Сервисы (заказы, склад, платежи, каталог) общаются между собой *синхронно* (где нужен немедленный результат, [6.1](06-01-sinhronnoe-vs-asinhronnoe.md)) и интенсивно. Контекст: высокая частота, нужна производительность, строгий контракт, полиглот (разные команды на разных языках). → **gRPC** (подход 3): бинарный, быстрый, типизированный контракт из protobuf, стриминг где надо. Это *внутри* периметра, браузер не участвует — ограничения gRPC (§2.2) не мешают.

**Публичный API для партнёров → REST.** Сторонние разработчики интегрируются с платформой (заказы через API, вебхуки). Контекст: публичный, разнородные потребители, важны повсеместность, простота, человекочитаемость, HTTP-кэширование, низкий порог входа. → **REST** (подход 2): все умеют REST, JSON читаем, OpenAPI документирует контракт, GET-эндпоинты кэшируются ([5.4](../05-dannye/05-04-strategii-keshirovaniya.md)). gRPC тут оттолкнул бы партнёров (бинарь, оснастка), GraphQL — избыточен и сложнее для простой интеграции.

**Мобильное и веб-приложение → GraphQL на границе.** Свои клиенты (мобильный, веб) имеют *разные* потребности в данных: мобильному нужен компактный набор полей (экономия трафика), вебу — больше; экраны показывают сложные вложенные данные (заказ + позиции + товары + статусы доставки) из *нескольких* сервисов. Контекст: разнородные клиенты, вложенные данные, агрегация источников, важно избежать over/under-fetching на мобильном. → **GraphQL на границе** (подход 4): клиент берёт ровно нужные поля одним запросом, GraphQL-слой агрегирует данные из внутренних сервисов (которые зовёт по gRPC, §2.5). N+1 решают батчингом (dataloader), запросы ограничивают по сложности (подход 6).

**Итог — сосуществование.** gRPC внутри (быстро, контракт), REST для партнёров (повсеместно, кэш), GraphQL для своих приложений (клиент-driven, агрегация) — три стиля под три контекста, слоями. GraphQL/REST на границе общаются с внутренними сервисами по gRPC. Это гибрид, как и везде в учебнике ([5.5](../05-dannye/05-05-batch-stream-konveery.md)).

**Поучительные ошибки.** Команда А, влюбившись в GraphQL, поставила его *везде*, включая простой внутренний CRUD-сервис конфигурации — получила N+1, сложные резолверы и трудность кэширования там, где простой REST/gRPC решил бы всё в разы проще (избыточность, §2.3, антипаттерн). Команда Б, наоборот, выставила *gRPC как публичный API* для партнёров — партнёры не смогли вызвать его из браузеров и привычных инструментов, жаловались на бинарь и оснастку; пришлось ставить REST-фасад (ограничение gRPC, §2.2). Обе ошиблись одинаково по сути: натянули *один* стиль на *чужой* контекст, игнорируя 2.4.

**Мораль кейса.** Стиль API выбирается *по контексту взаимодействия* (кто клиент, форма данных, требования — §2.4): gRPC для внутреннего быстрого, REST для публичного простого, GraphQL для клиент-driven вложенного. И они *сосуществуют слоями*, а не конкурируют за «один на всё». Это прямое приложение «инструмент под контекст, не под моду», прошившее весь учебник ([2.7](../02-stili/02-07-kak-vybirat-stil.md), [5.1](../05-dannye/05-01-vybor-hranilisch.md)).

## 6. Антипаттерны и ловушки

**Один стиль на всё по моде.** GraphQL/REST/gRPC «везде, потому что современно/привычно» (кейс). Натягивание на чужой контекст: GraphQL в простой CRUD (сложность), gRPC в публичный браузерный (нельзя вызвать), REST для высокочастотного внутреннего (производительность). Выбирай по контексту (§2.4).

**GraphQL для простого CRUD.** Избыточность (§2.3): резолверы, N+1, трудность кэша — там, где REST/gRPC проще. GraphQL окупается на разнородных клиентах и вложенных данных, не на тривиальном CRUD.

**gRPC как публичный/браузерный API.** Браузер не вызывает gRPC напрямую (нужен gRPC-Web/прокси), бинарь не читаем, оснастка отталкивает партнёров (§2.2, кейс). Для публичного — REST/GraphQL.

**Игнор болтливости/over-fetching REST.** Использовать REST для сильно связанных вложенных данных и страдать от множества запросов (under) или толстых ответов (over) — 2.1, [3.5](../03-dekompoziciya-ddd/03-05-granicy-servisov-i-moduley.md). Тогда GraphQL или агрегирующий эндпоинт уместнее.

**GraphQL без защиты от дорогих запросов.** Не ограничивать глубину/сложность запроса: клиент шлёт запрос, обходящий пол-графа → дорогая операция, DoS. Ограничивай сложность/глубину, тайм-ауты.

**Игнор N+1 в GraphQL.** Наивные резолверы делают запрос на каждый вложенный элемент: заказ с 50 позициями → 50+ запросов к БД. Используй батчинг (dataloader).

**Игнор связанности контракта.** Менять protobuf/GraphQL-схему, ломая клиентов (§2.6): строгий контракт тесно связывает. Планируй эволюцию/версионирование ([6.4](06-04-proektirovanie-api-versionirovanie.md)).

**Принудительно один стиль, где лучше сосуществование.** Запретить gRPC внутри ради «единообразия REST» или наоборот — теряешь сильные стороны под контекст (§2.5). Гибрид слоями — норма.

## 7. Ключевые выводы (чеклист)

- [ ] **REST** — ресурсы + HTTP-глаголы; повсеместность, простота, HTTP-кэш, человекочитаемость; страдает от **over/under-fetching**. Для публичного/CRUD/веб.
- [ ] **gRPC** — contract-first RPC, бинарный, HTTP/2, стриминг; производительность и строгий контракт; не для браузера/публичного. Для внутреннего сервис-сервис/высокой нагрузки.
- [ ] **GraphQL** — клиент выбирает поля, один запрос за вложенным графом; решает over/under-fetching; несёт N+1, сложность, трудность кэша. Для разнородных клиентов/вложенных данных/агрегации.
- [ ] Это **не конкуренты, а инструменты под контекст**: выбор диктуют **клиент, форма данных, требования** (производительность/кэш/контракт), не мода.
- [ ] Они **сосуществуют слоями**: gRPC внутри + REST/GraphQL на границе (мост к API Gateway/BFF [6.5](06-05-api-gateway-bff-service-mesh.md)).
- [ ] **Контракт/связанность** — компромисс: строгий (gRPC/GraphQL) безопасен, но связывает со схемой; REST гибче ценой строгости. Эволюцию планируй ([6.4](06-04-proektirovanie-api-versionirovanie.md)).
- [ ] Все три обычно **синхронны** ([6.1](06-01-sinhronnoe-vs-asinhronnoe.md)); асинхронный эквивалент — обмен сообщениями ([6.3](06-03-ocheredi-brokery-streaming-kafka.md)).
- [ ] Учитывай **ловушки**: GraphQL (N+1, сложность, DoS-запросы), gRPC (браузер, бинарь), REST (болтливость/over-fetching).

## 8. Упражнения и вопросы для самопроверки

**Вопросы на понимание**

1. Объясни over/under-fetching в REST и как GraphQL это решает. Какой ценой (что GraphQL приносит взамен)?
2. Для каждого стиля назови контекст, где он силён, и контекст, где он плох. Почему «лучшего» стиля нет?
3. Что значит «они сосуществуют слоями»? Приведи типичную композицию и объясни, почему gRPC внутри + REST/GraphQL на границе — разумно.

**Практика: выбор стиля**

4. Возьми API/взаимодействия в своей системе. Для каждого определи контекст (клиент, форма данных, требования) и реши, какой стиль уместен. Совпадает ли с тем, что используется? Где выбор был по моде?
5. Если у вас GraphQL — проверь на ловушки: есть ли защита от N+1 (батчинг)? ограничения сложности/глубины запроса? Если gRPC — как с браузером/публичным доступом? Если REST — нет ли болтливости/over-fetching на вложенных данных?

**Проектное задание**

6. Возьми код-пример из раздела 4. Для GraphQL-варианта смоделируй проблему N+1 (резолвер позиций делает запрос на каждую) и опиши решение через батчинг (dataloader). Для gRPC-варианта подумай: что нужно, чтобы вызвать его из браузерного приложения (подход 7)?
7. Спроектируй API-слой для системы по выбору с *разными* типами клиентов (внутренние сервисы, публичные партнёры, своё мобильное/веб приложение). Подбери стиль каждому контексту, покажи сосуществование слоями (что на границе, что внутри), и обоснуй каждый выбор через клиента+форму+требования (§2.4).
