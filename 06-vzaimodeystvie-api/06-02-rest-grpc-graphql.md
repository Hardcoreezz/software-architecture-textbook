# Глава 6.2. REST, gRPC, GraphQL

> Модуль 6. Взаимодействие сервисов и API
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

Когда взаимодействие синхронное (вызвал и ждёшь ответа, [6.1](06-01-sinhronnoe-vs-asinhronnoe.md)), встаёт следующий вопрос: в каком стиле строить API? Три доминирующих ответа — **REST, gRPC и GraphQL**. Их, как и архитектурные стили ([Модуль 2](../02-stili/README.md)), часто выбирают по моде или привычке: «REST, потому что все так делают», «GraphQL, потому что современно», «gRPC, потому что быстро». Отсюда решения не по делу: GraphQL в простом внутреннем CRUD (лишняя сложность), gRPC в публичном браузерном API (браузер не вызовет его напрямую), REST там, где нужны производительность и стриминг.

Главная мысль главы: **эти три стиля не конкурируют, а подходят разным контекстам**, и в одной системе обычно сосуществуют слоями (§2.5). Все три обычно синхронны; асинхронный эквивалент — обмен сообщениями ([6.3](06-03-ocheredi-brokery-streaming-kafka.md)).

---

## 2. Теория

### 2.1. REST

**REST (Representational State Transfer)** — ресурсный стиль поверх HTTP. Ресурсы адресуются URL (`/orders/123`), действия выражаются HTTP-глаголами (GET, POST, PUT, DELETE), а коды статусов и кэширование берутся из семантики HTTP. Сервер не хранит состояние сессии между запросами (stateless).

*Сильные стороны.* REST понимают все, инструментов для него множество, клиенту хватает любой HTTP-библиотеки. GET-ответы кэшируются стандартными средствами HTTP — в прокси и CDN ([5.4](../05-dannye/05-04-strategii-keshirovaniya.md)). JSON легко читать и отлаживать.

*Слабые стороны.* Главная — **over/under-fetching**. Форму ответа задаёт сервер, и клиент либо получает лишнее (over-fetching), либо ходит за связанными данными несколькими запросами (under-fetching), что оборачивается болтливостью по сети ([4.1](../04-raspredelennye-sistemy/04-01-zabluzhdeniya-i-setevye-osnovy.md)). Контракт по умолчанию слабый (§2.6). Для RPC-вызовов и стриминга REST неудобен.

### 2.2. gRPC

**gRPC** — RPC-фреймворк поверх HTTP/2 с подходом «сначала контракт» (contract-first): схему пишут на Protocol Buffers (protobuf) и генерируют из неё код клиента и сервера. Данные идут в бинарном виде, удалённый метод вызывается как обычная функция, поддерживается стриминг, в том числе двунаправленный.

*Сильные стороны.* Высокая производительность за счёт бинарного формата и мультиплексирования HTTP/2, строгий типизированный контракт, потоковые вызовы и одна схема для сервисов на разных языках.

*Слабые стороны.* Бинарный трафик не прочитать глазами, отлаживать труднее. Браузер не поддерживает gRPC напрямую: нужен gRPC-Web — через прокси или поддержку на сервере. Оснастка сложнее. RPC-стиль связывает клиента с набором методов сервиса теснее, чем ресурсная модель REST.

### 2.3. GraphQL

**GraphQL** — язык запросов к API: клиент перечисляет нужные поля и получает их одним запросом. Данные описаны строго типизированной схемой, конечная точка (endpoint) обычно одна.

*Сильные стороны.* Ответ формирует клиент, поэтому over/under-fetching исчезает, а вложенные данные (заказ, позиции, клиент) приходят разом. Схему можно запросить у самого сервера (интроспекция). Один GraphQL-слой может агрегировать несколько источников данных.

*Слабые стороны.* Значение каждого поля достаёт **резолвер** — функция на сервере. Наивные резолверы порождают **проблему N+1 запросов**: отдельный запрос к БД на каждый вложенный элемент ([8.4](../08-nadezhnost-nablyudaemost-proizvoditelnost/08-04-proizvoditelnost-profilirovanie.md)). Запросы обычно идут POST на одну конечную точку, поэтому стандартный HTTP-кэш не работает. Клиент может прислать сколь угодно глубокий или сложный запрос — это ловушка производительности и вектор DoS-атаки. Для простого API всё это избыточно.

### 2.4. Это не конкуренты — это инструменты под контекст

«Лучшего» стиля нет. Выбор диктуют три вопроса:
- **Кто клиент?** Браузер, мобильное приложение, внутренний сервис, сторонний разработчик или несколько разнородных клиентов.
- **Какая форма данных?** Простой CRUD, вложенный граф или поток.
- **Какие требования?** Производительность, строгость контракта, кэширование, человекочитаемость.

Сводка ниже — сигналы, а не жёсткие правила:

| Стиль | Где силён | Где плох |
|:---|:---|:---|
| REST | публичные API, CRUD, веб; важны HTTP-кэш, повсеместность, простота | вложенные данные для разных клиентов; высокочастотный внутренний трафик, стриминг |
| gRPC | внутреннее взаимодействие сервисов, высокая нагрузка, стриминг, разные языки, строгий контракт | публичный и браузерный API |
| GraphQL | разнородные клиенты с разными нуждами в данных, вложенные данные, агрегация источников | простой CRUD |

### 2.5. Они сосуществуют

Частый и правильный паттерн — **gRPC между сервисами внутри и REST или GraphQL на границе**. Клиент обращается к пограничному слою, а тот зовёт внутренние сервисы по gRPC. Это тот же послойный выбор, что и с архитектурными стилями ([2.7](../02-stili/02-07-kak-vybirat-stil.md)). Как устроен сам пограничный слой — шлюз (API Gateway) или отдельный API под каждого клиента (BFF), — разбирает [6.5](06-05-api-gateway-bff-service-mesh.md).

### 2.6. Контракт и связанность

Стили различаются строгостью контракта. У **gRPC и GraphQL** строгая схема: генерация кода, проверка типами, оснастка и правила совместимой эволюции ([6.4](06-04-proektirovanie-api-versionirovanie.md)). У **REST** — соглашения плюс OpenAPI: начать проще, но контракт слабее, и несовместимое изменение легче пропустить.

Клиент зависит от формы ответа в любом стиле. Сама по себе строгая схема не делает эту связь теснее, а делает её явной: несовместимое изменение можно поймать автоматической сверкой версий схемы до выкладки, а не по ошибкам клиентов в продакшене. Цена — оснастка и дисциплина работы со схемой.

## 3. Подходы

**Подход 1. Выбирай стиль для каждого взаимодействия отдельно** — по трём вопросам §2.4. «Так модно» и «у нас все так делают» не отвечают ни на один из них.

**Подход 2. Комбинируй слоями** (§2.5) и не требуй одного стиля на всю систему.

**Подход 3. Бери GraphQL вместе с защитой.** С первого дня собирай обращения резолверов к БД в пакетные запросы (паттерн dataloader), ограничивай глубину и сложность запросов, ставь тайм-ауты, продумай кэширование. Если команда не готова платить эту цену, GraphQL не бери.

**Подход 4. Для gRPC заранее реши вопрос браузера и отладки**: gRPC-Web для вызовов из браузера, оснастка для бинарного трафика. Публичный браузерный API на gRPC без веской причины не строй.

## 4. Пример кода: одна операция — три стиля

Получим заказ с позициями и данными клиента в каждом из трёх стилей. Сначала REST.

```typescript
// REST: ресурсы и HTTP-глаголы. Связанные данные — отдельными запросами (under-fetching).
const order = await fetch(`/orders/123`).then((r) => r.json());
const lines = await fetch(`/orders/123/lines`).then((r) => r.json());
const customer = await fetch(`/customers/${order.customerId}`).then((r) => r.json());
// Три запроса — или один «толстый» эндпоинт, который всегда отдаёт всё (over-fetching).
```

Теперь gRPC: типизированный вызов по бинарному контракту.

```protobuf
syntax = "proto3";

// Контракт: строгая схема, из неё генерируется код клиента и сервера.
service OrderService {
  rpc GetOrder(GetOrderRequest) returns (OrderReply);
}
message GetOrderRequest { string order_id = 1; }
message OrderLine { string sku = 1; int32 qty = 2; }
message Customer { string name = 1; }
message OrderReply {
  string order_id = 1;
  repeated OrderLine lines = 2; // вложенные данные в одном бинарном ответе
  Customer customer = 3;
}
```

```typescript
// Вызов через клиент, сгенерированный из схемы: типизированно, бинарно, по HTTP/2.
const reply = await orderClient.getOrder({ orderId: "123" }); // один вызов
```

И GraphQL: клиент сам выбирает поля.

```typescript
// GraphQL: только нужные поля, всё одним запросом.
const query = `
  query {
    order(id: "123") {
      id
      lines { sku qty }   # только нужные поля позиций
      customer { name }   # только имя, а не весь объект клиента
    }
  }`;
const data = await fetch(`/graphql`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ query }),
}).then((r) => r.json());
```

Лучшего варианта здесь нет. REST платит лишними запросами или лишними данными, gRPC — оснасткой и недоступностью из браузера напрямую, GraphQL — сложностью сервера (§2.3). А GraphQL- или REST-слой на границе вполне может внутри звать `OrderService` по gRPC (§2.5).

## 5. Развёрнутый кейс: API-стили платформы по контексту

У платформы три типа клиентов. Подберём стиль под каждый — и получим три стиля, работающих слоями.

**Внутреннее взаимодействие сервисов → gRPC.** Сервисы заказов, склада, платежей и каталога часто зовут друг друга синхронно — там, где нужен немедленный результат ([6.1](06-01-sinhronnoe-vs-asinhronnoe.md)). Важны производительность и строгий контракт, команды пишут на разных языках. Браузер здесь не участвует, поэтому ограничения gRPC (§2.2) не мешают.

**Публичный API для партнёров → REST.** Сторонние разработчики создают заказы через API и получают вебхуки. Потребители разнородны, нужен низкий порог входа: REST умеют все, OpenAPI документирует контракт, GET-эндпоинты кэшируются. gRPC оттолкнул бы партнёров бинарным форматом и оснасткой, а GraphQL для простой интеграции избыточен.

**Мобильное и веб-приложение → GraphQL на границе.** Мобильному нужен компактный набор полей (экономия трафика), вебу — больше, а экраны показывают вложенные данные из нескольких сервисов: заказ, позиции, товары, статусы доставки. Каждый клиент берёт только нужные поля одним запросом, а GraphQL-слой собирает их из внутренних сервисов. Альтернатива — отдельный BFF под каждого клиента ([6.5](06-05-api-gateway-bff-service-mesh.md)); здесь один GraphQL-слой закрывает разные нужды тем, что клиент сам выбирает поля. N+1 и дорогие запросы закрывают по подходу 3.

В итоге REST и GraphQL стоят на границе, а внутрь оба ходят по gRPC.

**Поучительные ошибки.** Команда А, увлёкшись GraphQL, поставила его везде, включая простой внутренний CRUD-сервис конфигурации. Она получила N+1, сложные резолверы и проблемы с кэшем там, где REST или gRPC решили бы задачу в разы проще. Команда Б выставила gRPC публичным API для партнёров. Те не смогли вызвать его из браузеров и привычных инструментов, жаловались на бинарный формат и оснастку — пришлось ставить REST-фасад. Ошибка у обеих одна: стиль натянули на чужой контекст, не задав вопросов §2.4.

## 6. Антипаттерны и ловушки

**Один стиль на всё.** Стиль натягивают на чужой контекст по моде, как команды А и Б в кейсе, или ради «единообразия»: запрещают gRPC внутри, потому что «у нас стандарт — REST». Так теряются сильные стороны стиля, который подходит контексту.

**Болтливый REST на вложенных данных.** На сильно связанных данных клиент страдает от множества запросов (under-fetching) или толстых ответов (over-fetching). Здесь уместнее GraphQL или агрегирующий эндпоинт.

**GraphQL без защиты.** Наивные резолверы делают запрос на каждый вложенный элемент: заказ с 50 позициями — 50+ запросов к БД. Без лимитов глубины и сложности клиент присылает запрос, обходящий полграфа, и кладёт сервер (DoS). Защита — в подходе 3.

**Несовместимая смена схемы.** Правка protobuf- или GraphQL-схемы в обход правил совместимости (например, переиспользованный номер поля protobuf) ломает уже развёрнутых клиентов. Строгая схема позволяет поймать такое изменение проверкой (§2.6), но сама по себе от него не защищает. Эволюцию контракта планируй по [6.4](06-04-proektirovanie-api-versionirovanie.md).

---

## 7. Ключевые выводы (чеклист)

- [ ] **REST** — для публичных API, CRUD и веба; **gRPC** — для внутреннего взаимодействия сервисов; **GraphQL** — для разнородных клиентов и вложенных данных.
- [ ] Стиль выбирают по **клиенту, форме данных и требованиям**, а не по моде; в одной системе стили **сосуществуют слоями**.
- [ ] У каждого стиля своя ловушка: REST — over/under-fetching, gRPC — браузер и бинарный трафик, GraphQL — N+1 и дорогие запросы. Защиту закладывай сразу.
- [ ] Несовместимое изменение строгой схемы можно поймать проверкой до выкладки, в REST без спецификации — нет. Эволюцию планируй заранее ([6.4](06-04-proektirovanie-api-versionirovanie.md)).
- [ ] Все три обычно синхронны; асинхронный эквивалент — обмен сообщениями ([6.3](06-03-ocheredi-brokery-streaming-kafka.md)).

## 8. Упражнения и вопросы для самопроверки

**Вопросы на понимание**

1. Объясни over/under-fetching в REST и как его решает GraphQL. Что GraphQL приносит взамен?
2. Где каждый стиль силён и где плох? Почему «лучшего» стиля нет?
3. Что значит «сосуществуют слоями»? Почему gRPC внутри и REST/GraphQL на границе — разумная композиция?

**Практика: выбор стиля**

4. Для каждого взаимодействия своей системы определи клиента, форму данных и требования и реши, какой стиль уместен. Совпадает ли это с тем, что используется? Где выбор был по моде?
5. Проверь свои API на ловушки: в GraphQL — батчинг против N+1 и лимиты глубины и сложности запросов; в gRPC — доступ из браузера и для внешних потребителей; в REST — болтливость и over-fetching на вложенных данных.

**Проектное задание**

6. Возьми код-пример из раздела 4. Для GraphQL смоделируй N+1 (резолвер позиций делает запрос на каждую) и опиши решение через батчинг (dataloader). Для gRPC подумай, что нужно, чтобы вызвать его из браузерного приложения (подход 4).
7. Спроектируй API-слой для системы с разными клиентами: внутренние сервисы, внешние партнёры, своё мобильное и веб-приложение. Подбери стиль каждому, покажи, что стоит на границе, а что внутри, и обоснуй выбор тремя вопросами §2.4.

## 9. Что почитать дальше

- **Roy Fielding, диссертация о REST (и популярные разборы).** Первоисточник: ресурсы, stateless, HATEOAS (ссылки на возможные действия прямо в ответе).
- **gRPC и Protocol Buffers, официальная документация.** Контракт, стриминг, производительность, gRPC-Web.
- **GraphQL (graphql.org) и «Production Ready GraphQL» (Marc-André Giroux).** Схема, резолверы, N+1, сложность запросов, безопасность.
- **Sam Newman. «Building Microservices», главы об API и коммуникации.** Сравнение стилей между сервисами и их сосуществование.
- **«Designing Web APIs» (Brenda Jin и др.); статьи Phil Sturgeon о REST, gRPC и GraphQL.** Практический выбор стиля под контекст.
