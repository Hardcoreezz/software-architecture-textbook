# Глава 3.4. DDD тактический: агрегаты, сущности, value objects

> Модуль 3. Декомпозиция и доменное проектирование
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

Стратегический DDD ([3.3](03-03-ddd-strategicheskiy.md)) нашёл *границы* — ограниченные контексты, ставшие границами модулей и сервисов. Но что находится *внутри* контекста? Там живёт бизнес-логика — та самая богатая модель, которую гексагональная архитектура ([2.2](../02-stili/02-02-sloistaya-lukovichnaya-geksagonalnaya-clean.md)) ставит в центр и защищает от инфраструктуры. Тактический DDD — это набор строительных блоков, позволяющих смоделировать эту логику так, чтобы *бизнес-правила (инварианты) всегда соблюдались*, а модель оставалась согласованной и выразительной.

Это спуск со стратегического уровня (где провести границы) на тактический (как устроить внутренность). И спуск важный: даже идеально найденные границы не спасут, если внутри — анемичная свалка данных без логики, где инварианты нарушаются, потому что их некому защищать. Тактический DDD — противоядие от анемичной модели (главный антипаттерн этой главы) и способ построить тот «богатый домен», ради которого вообще нужна гексагональная архитектура.

Главный блок главы — **агрегат**: он определяет *границы согласованности*, и это, пожалуй, самое практически важное тактическое решение. Остальные блоки (value objects, сущности, доменные события, репозитории) — вокруг него. Важная оговорка с самого начала (эхо §2.2): тактический DDD окупается для *богатого, сложного домена* — обычно ядра. Для тонкого CRUD это over-engineering. Применяй там, где есть нетривиальные правила, которые надо защищать.

## 2. Теория

### 2.1. Объект-значение (Value Object)

**Объект-значение** определяется *своими атрибутами*, не имеет идентичности и неизменяем. Два value object с одинаковыми атрибутами *равны* и взаимозаменяемы: `Money(100, "USD")` равно любому другому `Money(100, "USD")` — это одна и та же «сотня долларов», неважно какой экземпляр.

Свойства:
- **Неизменяемость (immutable):** value object не меняется; «изменение» — это создание нового (как у строк/чисел).
- **Равенство по значению:** сравниваются по атрибутам, не по ссылке.
- **Самовалидация:** value object не может существовать в невалидном состоянии (нельзя создать `Email` без `@`, `Money` с отрицательной валютой).
- **Выразительность:** заменяет «голые» примитивы доменными понятиями.

Примеры: `Money`, `Address`, `DateRange`, `Email`, `Quantity`, `Coordinates`. Главная польза для архитектора — борьба с *одержимостью примитивами* (primitive obsession): когда деньги — это `number`, email — `string`, а количество — тоже `number`, их легко перепутать, нельзя гарантировать валидность, и доменные правила размазаны. Value object инкапсулирует и значение, и его правила.

### 2.2. Сущность (Entity)

**Сущность** имеет *идентичность*, которая сохраняется во времени, даже когда атрибуты меняются. Два заказа с одинаковыми атрибутами, но разными id — это *разные* заказы; один и тот же заказ с изменившимся статусом — это *тот же* заказ. Сущность *изменяема* и имеет жизненный цикл.

Примеры: `Order`, `Customer`, `Account`, `Shipment`. У них есть «личность»: важно отличать «этот» от «того» и отслеживать «один и тот же» во времени.

### 2.3. Сущность vs value object: вопрос идентичности

Как выбрать? Главный вопрос: **важна ли идентичность?** — «это *тот же самый* объект во времени, или просто значение?».

- Деньги, адрес, дата — *значения*: тебе всё равно, «тот же» это экземпляр стодолларовой купюры или другой; важна только сумма. → value object.
- Заказ, клиент, счёт — *сущности*: важно, «тот же» это заказ или другой, и отследить его во времени. → entity.

Практический совет, который часто упускают: **по умолчанию делай value object, а сущность — только если идентичность реально нужна.** Value object'ов в хорошей модели обычно гораздо больше, чем сущностей, и они снимают массу багов (неизменяемость, валидность, равенство по значению).

### 2.4. Агрегат (Aggregate) — центральный блок

**Агрегат** — кластер сущностей и value object, рассматриваемый как *единое целое для обеспечения согласованности*. У агрегата есть **корень агрегата (aggregate root)** — единственная точка входа. Правила агрегата:

1. **Агрегат защищает инварианты** — бизнес-правила, которые *всегда* должны выполняться — внутри своей границы. Например: «сумма заказа = сумме строк»; «нельзя снять больше баланса».
2. **Внешние ссылки — только на корень**, никогда на внутренние сущности агрегата. Внешний мир общается с агрегатом через корень.
3. **Агрегат — граница согласованности/транзакции:** изменения внутри агрегата атомарны и согласованы. Один агрегат меняется в одной транзакции.
4. **На другие агрегаты ссылайся по идентификатору (id), а не прямой ссылкой на объект.** Заказ ссылается на `customerId`, а не держит объект `Customer`.

Почему агрегат — главный блок: **граница агрегата = граница согласованности.** Инвариант, который должен выполняться *всегда и немедленно* (например, «остаток не уходит в минус»), обязан жить *внутри одного агрегата* — только там его можно защитить атомарно. Если инвариант охватывает несколько агрегатов, его нельзя гарантировать в одной транзакции — придётся принимать согласованность в конечном счёте (саги, [Модуль 4](../04-raspredelennye-sistemy/README.md)). Поэтому проектирование агрегатов = решение о том, *что должно быть согласовано немедленно, а что может быть согласовано позже*.

### 2.5. Размер агрегата: чем меньше, тем лучше

Ключевое (и часто нарушаемое) правило: **делай агрегаты маленькими.** Включай в агрегат только то, что *обязано* быть согласовано немедленно (то, что связано инвариантом). Причины:

- **Граница транзакции/блокировки.** Большой агрегат = большая транзакция = больше конкуренции/блокировок = хуже параллелизм и масштабируемость (прямая связь с производительностью и согласованностью под конкуренцией, [1.4](../01-atributy-kachestva/01-04-scenarii-kachestva.md)).
- **Меньше конфликтов.** Мелкий агрегат реже становится точкой состязания при конкурентных изменениях.

Соблазн «втянуть всё связанное в один агрегат» (заказ + клиент + все товары + история) ведёт к огромному агрегату-блобу с чудовищной конкуренцией. Правильно: включи в агрегат только то, что связано *инвариантом немедленной согласованности*; всё остальное — отдельные агрегаты, ссылка по id, согласованность в конечном счёте. Это прямое приложение [1.5](../01-atributy-kachestva/01-05-upravlenie-kompromissami.md) (что приоритетнее — согласованность или доступность/масштаб) на уровне модели.

### 2.6. Доменные события, сервисы, репозитории, фабрики

Вокруг агрегата — ещё блоки:

- **Доменное событие (domain event):** факт, произошедший в домене (`OrderConfirmed`). Агрегаты их порождают; так агрегаты сообщают миру об изменениях, не зная потребителей (прямая связь с EDA, [2.4](../02-stili/02-04-event-driven-architecture.md), и с согласованностью между агрегатами через события).
- **Доменный сервис (domain service):** логика, которая не принадлежит естественно ни одной сущности/value object — обычно операция, охватывающая *несколько* агрегатов или внешнее знание. Не свалка («не знаю куда — суну в сервис»), а именно операции без естественного дома в одном объекте.
- **Репозиторий (repository):** даёт доступ к агрегатам (загрузить/сохранить). Это *порт* из гексагональной ([2.2](../02-stili/02-02-sloistaya-lukovichnaya-geksagonalnaya-clean.md)): домен объявляет интерфейс репозитория, инфраструктура реализует. Правило: **один репозиторий на корень агрегата** (репозиторий работает с агрегатами целиком, не с их внутренностями).
- **Фабрика (factory):** инкапсулирует сложное создание агрегата/сущности, когда конструктор недостаточен.

### 2.7. Как блоки складываются (и связь с гексагональной)

Картина целиком: value object'ы и сущности *компонуются* в агрегаты; агрегат имеет корень, защищающий инварианты; доступ к агрегатам — через репозитории (порты); изменения порождают доменные события. Это и есть «богатый домен» в центре гексагональной архитектуры: тактический DDD — *способ построить этот центр правильно*. Анемичная модель (данные без логики, логика в сервисах) — провал этого центра: защищать инварианты некому, и гексагональная защищает пустоту.

## 3. Подходы

**Подход 1. Убей одержимость примитивами — моделируй значения как value objects.** Деньги, email, количество, диапазон — не `number`/`string`, а value object с самовалидацией, неизменяемостью и равенством по значению (§2.1). Это снимает целый класс багов и делает модель выразительной.

**Подход 2. Выбирай entity vs value object по идентичности.** Спроси: «это *тот же самый* объект во времени или просто значение?». По умолчанию — value object; сущность — только если идентичность реально нужна (§2.3).

**Подход 3. Проектируй агрегаты вокруг инвариантов.** Спроси: «какие правила должны выполняться *всегда и немедленно*?». То, что связано таким инвариантом, — в один агрегат (граница согласованности, §2.4). Это главное тактическое решение.

**Подход 4. Делай агрегаты маленькими.** Включай только то, что обязано быть немедленно согласовано. Остальное — отдельные агрегаты, ссылка по id, согласованность в конечном счёте (§2.5). Большой агрегат убивает параллелизм.

**Подход 5. Защищай инварианты в корне; не выставляй сеттеры.** Изменения — через осмысленные доменные методы (`order.addLine(...)`, `account.withdraw(...)`), которые проверяют инварианты, а не через публичные сеттеры, позволяющие привести объект в невалидное состояние. Внешний доступ — только к корню, не к внутренностям.

**Подход 6. Ссылайся на другие агрегаты по id.** Заказ хранит `customerId`, не объект `Customer`. Это держит границы агрегатов чёткими и предотвращает разрастание транзакций.

**Подход 7. Связывай агрегаты через доменные события.** Что не может быть в одной транзакции (разные агрегаты) — согласовывай через доменные события и согласованность в конечном счёте (2.6, мост к EDA [2.4](../02-stili/02-04-event-driven-architecture.md) и сагам [Модуля 4](../04-raspredelennye-sistemy/README.md)).

**Подход 8. Применяй тактический DDD к богатому домену, не к CRUD.** Сложные правила, инварианты, ядро ([3.3](03-03-ddd-strategicheskiy.md)) — да. Тонкий CRUD (принял-записал) — нет, это over-engineering (эхо §2.2). Дозируй по сложности домена.

## 4. Пример кода: богатый агрегат vs анемичная модель

Сначала — *анемичная* модель (антипаттерн): данные с публичными сеттерами, логика снаружи. Инварианты никто не защищает.

```typescript
// ПЛОХО (анемичная модель): мешок данных + логика в сервисе. Инварианты беззащитны.
class Order {
  id!: string;
  status!: string;
  lines: { sku: string; qty: number; price: number }[] = [];
  total = 0; // можно выставить ЛЮБОЕ значение, рассинхронив с lines
}

class OrderService {
  addLine(order: Order, sku: string, qty: number, price: number): void {
    order.lines.push({ sku, qty, price });
    order.total += qty * price; // легко забыть; легко рассинхронить
    // Ничто не мешает добавить строку в уже отправленный заказ — инвариант не защищён.
  }
}
```

Теперь — *богатый* агрегат: корень защищает инварианты, value object для денег, методы вместо сеттеров, ссылка на клиента по id.

```typescript
// === Value Object: деньги. Неизменяемы, равны по значению, самовалидируются (§2.1). ===
class Money {
  private constructor(readonly amount: number, readonly currency: string) {
    if (amount < 0) throw new DomainError("Деньги не могут быть отрицательными");
  }
  static of(amount: number, currency: string): Money {
    return new Money(amount, currency);
  }
  add(other: Money): Money {
    if (other.currency !== this.currency) throw new DomainError("Разные валюты");
    return Money.of(this.amount + other.amount, this.currency); // новый объект, не мутация
  }
  equals(o: Money): boolean {
    return this.amount === o.amount && this.currency === o.currency; // равенство по значению
  }
}

// === Сущность-часть агрегата: строка заказа ===
class OrderLine {
  constructor(readonly sku: string, readonly qty: number, readonly price: Money) {
    if (qty <= 0) throw new DomainError("Количество должно быть > 0"); // самовалидация
  }
  get subtotal(): Money {
    return Money.of(this.price.amount * this.qty, this.price.currency);
  }
}

// === КОРЕНЬ АГРЕГАТА: Order. Единственная точка входа, защищает инварианты (§2.4). ===
class Order {
  private _lines: OrderLine[] = [];
  private _status: "draft" | "confirmed" | "shipped" = "draft";
  private _events: DomainEvent[] = []; // доменные события (§2.6)

  constructor(
    readonly id: string,
    readonly customerId: string, // ссылка на ДРУГОЙ агрегат по ID, не объектом (§2.6, подход 6)
    readonly currency: string,
  ) {}

  // Изменение — через осмысленный метод, а не сеттер (подход 5).
  addLine(sku: string, qty: number, price: Money): void {
    // ИНВАРИАНТ: нельзя менять подтверждённый/отправленный заказ. Защищён здесь.
    if (this._status !== "draft") throw new DomainError("Заказ уже подтверждён");
    if (price.currency !== this.currency) throw new DomainError("Валюта строки не совпадает");
    this._lines.push(new OrderLine(sku, qty, price));
  }

  confirm(): void {
    if (this._lines.length === 0) throw new DomainError("Пустой заказ нельзя подтвердить");
    this._status = "confirmed";
    this._events.push({ type: "OrderConfirmed", orderId: this.id }); // событие (§2.6)
  }

  // ИНВАРИАНТ "total = сумма строк" не хранится отдельно, а ВЫЧИСЛЯЕТСЯ — рассинхрон невозможен.
  get total(): Money {
    return this._lines.reduce((sum, l) => sum.add(l.subtotal), Money.of(0, this.currency));
  }

  get lines(): ReadonlyArray<OrderLine> { return this._lines; } // только чтение наружу
  pullEvents(): DomainEvent[] { const e = this._events; this._events = []; return e; }
}
```

**Что показывает пример.** Анемичный `Order` — мешок данных с публичными полями: `total` можно рассинхронить с `lines`, строку можно добавить в отправленный заказ — *инварианты беззащитны*, потому что нет хозяина, который их охраняет (главный антипаттерн). Богатый агрегат всё переворачивает: `Money` — value object (неизменяемый, равный по значению, самовалидирующийся — подход 1, убивает primitive obsession); изменения идут через осмысленные методы (`addLine`, `confirm`), а не сеттеры (подход 5); инвариант «нельзя менять подтверждённый заказ» защищён *внутри* корня; инвариант «total = сумма строк» не хранится, а *вычисляется* — рассинхрон физически невозможен. Заметь подход 6: заказ ссылается на `customerId` (id другого агрегата), а не держит объект `Customer` — границы агрегатов чёткие, транзакция не разрастается. И `pullEvents` — мост к EDA ([2.4](../02-stili/02-04-event-driven-architecture.md)): агрегат порождает доменное событие `OrderConfirmed`, не зная потребителей. Это и есть «богатый домен» в центре гексагональной ([2.2](../02-stili/02-02-sloistaya-lukovichnaya-geksagonalnaya-clean.md)) — построенный так, что инварианты защищать *есть кому*.

## 5. Развёрнутый кейс: где провести границу агрегата (склад снова)

Вернёмся к складскому учёту из [1.3](../01-atributy-kachestva/01-03-asr-i-kak-ih-vytaskivat.md)/[1.4](../01-atributy-kachestva/01-04-scenarii-kachestva.md): критичный инвариант — «остаток товара не уходит в минус под конкурентным доступом» (вытащенный ASR). Тактический DDD отвечает на вопрос: *какой агрегат* защищает этот инвариант и *где его граница*.

**Главный вопрос (подход 3): что должно быть согласовано немедленно?** Инвариант «остаток ≥ 0» должен выполняться *атомарно* при каждом списании — иначе двое спишут последнюю единицу (гонка из [1.4](../01-atributy-kachestva/01-04-scenarii-kachestva.md)). Значит, *остаток конкретного товара* и операция его изменения обязаны жить *внутри одного агрегата* (граница согласованности, §2.4). Это диктует агрегат `StockItem` (товар + его остаток + операции списания/пополнения), защищающий инвариант в корне:

```typescript
class StockItem { // корень агрегата; граница согласованности для ОДНОГО товара
  private _quantity: number;
  reserve(qty: number): void {
    if (qty > this._quantity) throw new InsufficientStockError(); // ИНВАРИАНТ остаток ≥ 0
    this._quantity -= qty;
  }
}
```

**Ошибка размера — слишком большой агрегат (подход 4).** Соблазн: сделать один агрегат `Warehouse`, содержащий *все* товары склада, и в нём защищать остатки. Катастрофа для параллелизма: любое списание *любого* товара блокирует *весь* склад (граница транзакции = весь warehouse), 50 000 покупателей билетов… простите, кладовщиков, встают в очередь за одной блокировкой. Огромный агрегат = огромная конкуренция (§2.5, прямая связь с производительностью из [1.4](../01-atributy-kachestva/01-04-scenarii-kachestva.md)). Правильно: агрегат — *один товар* (`StockItem`), а не весь склад. Тогда списания разных товаров идут параллельно, конкурируя только за свой `StockItem`.

**Ошибка размера — слишком маленький/раздробленный.** Если бы остаток и операция списания оказались в *разных* агрегатах, инвариант «остаток ≥ 0» пересекал бы границу агрегатов — и его нельзя было бы защитить атомарно (пришлось бы городить распределённую согласованность там, где она не нужна). Инвариант *определяет* минимальную границу агрегата: всё, что он связывает, — внутри.

**Что — наружу, через события.** «Уведомить отдел закупок, когда остаток ниже порога» — это *не* инвариант немедленной согласованности. Это может произойти чуть позже. Значит — *не* в агрегат `StockItem`, а через доменное событие `StockLowered` → отдельный реагирующий (подход 7, EDA [2.4](../02-stili/02-04-event-driven-architecture.md)). Согласованность в конечном счёте здесь приемлема ([1.5](../01-atributy-kachestva/01-05-upravlenie-kompromissami.md)).

**Мораль кейса.** Граница агрегата — это решение «что согласуется немедленно, что — позже», и его диктует *инвариант*. Инвариант «остаток ≥ 0» → агрегат `StockItem` (один товар). Не больше (иначе убьём параллелизм — кейс билетов и склад из [1.4](../01-atributy-kachestva/01-04-scenarii-kachestva.md)) и не меньше (иначе инвариант не защитить атомарно). Всё, что не инвариант немедленной согласованности, выносится через события в согласованность в конечном счёте. Это тактический DDD, напрямую решающий ASR из [Модуля 1](../01-atributy-kachestva/README.md) и компромисс «согласованность vs масштаб» из [1.5](../01-atributy-kachestva/01-05-upravlenie-kompromissami.md) — на уровне модели.

## 6. Антипаттерны и ловушки

**Анемичная модель (anemic domain model).** Главный антипаттерн (раздел §4): сущности — мешки данных с публичными сеттерами, вся логика в сервисах. Инварианты беззащитны, домен «пуст», гексагональная ([2.2](../02-stili/02-02-sloistaya-lukovichnaya-geksagonalnaya-clean.md)) защищает пустоту. Логика должна жить *в* модели, а не вокруг неё.

**Одержимость примитивами (primitive obsession).** Деньги — `number`, email — `string`, количество — `number`. Их легко перепутать, нельзя гарантировать валидность, правила размазаны. Моделируй значения как value objects (подход 1).

**Слишком большой агрегат.** Втянуть всё связанное в один агрегат (весь склад, заказ со всем клиентом и историей). Огромная транзакция, конкуренция, убитый параллелизм и масштаб (§2.5, кейс). Включай только связанное инвариантом немедленной согласованности.

**Слишком маленький/раздробленный агрегат.** Разнести по разным агрегатам то, что связано инвариантом немедленной согласованности. Инвариант пересекает границу → его нельзя защитить атомарно → лишняя распределённая согласованность. Инвариант задаёт минимальную границу.

**Прямые ссылки на внутренности чужого агрегата.** Держать объект другого агрегата вместо ссылки по id (нарушение §2.4, подход 6). Размывает границы, разрастает транзакции, плодит связанность.

**Обход корня агрегата.** Менять внутренние сущности агрегата напрямую, минуя корень. Инварианты, которые корень должен защищать, обходятся. Доступ — только через корень.

**Изменяемые value objects.** Сделать value object с сеттерами/мутацией. Теряются гарантии (общий экземпляр меняется неожиданно, равенство по значению ломается). Value object неизменяем — «изменение» = новый объект.

**Инвариант снаружи агрегата.** Проверять бизнес-правило в сервисе/контроллере вместо агрегата. Тогда правило можно обойти (другой путь к данным его не проверит). Инвариант защищается *внутри* агрегата, единообразно.

**Тактический DDD на тонком CRUD.** Городить агрегаты, value objects, репозитории и фабрики для «принял-записал» без правил. Сложность без отдачи (over-engineering, §2.2, подход 8). Дозируй по богатству домена.

## 7. Ключевые выводы (чеклист)

- [ ] **Value object** — определяется атрибутами, без идентичности, неизменяем, равен по значению, самовалидируется. Убивает **primitive obsession**.
- [ ] **Сущность** — имеет идентичность во времени, изменяема. Выбор entity/VO — по вопросу «**важна ли идентичность?**»; по умолчанию — value object.
- [ ] **Агрегат** — кластер с **корнем** (единственная точка входа), защищающим **инварианты**; внешние ссылки — только на корень.
- [ ] **Граница агрегата = граница согласованности/транзакции**: инвариант немедленной согласованности обязан жить внутри одного агрегата.
- [ ] **Делай агрегаты маленькими** — только то, что связано инвариантом немедленной согласованности; большой агрегат убивает параллелизм (связь с [1.4](../01-atributy-kachestva/01-04-scenarii-kachestva.md), [1.5](../01-atributy-kachestva/01-05-upravlenie-kompromissami.md)).
- [ ] На другие агрегаты ссылайся **по id**; связывай агрегаты через **доменные события** и согласованность в конечном счёте (мост к EDA [2.4](../02-stili/02-04-event-driven-architecture.md), сагам [Модуля 4](../04-raspredelennye-sistemy/README.md)).
- [ ] Изменения — через **осмысленные методы**, не сеттеры; инварианты защищай **в корне**, не снаружи.
- [ ] **Репозиторий — порт** (один на корень агрегата); это и есть «богатый домен» в центре гексагональной ([2.2](../02-stili/02-02-sloistaya-lukovichnaya-geksagonalnaya-clean.md)).
- [ ] Главный антипаттерн — **анемичная модель**; применяй тактический DDD к **богатому домену**, не к CRUD.

## 8. Упражнения и вопросы для самопроверки

**Вопросы на понимание**

1. Чем value object отличается от сущности? Сформулируй главный вопрос для выбора между ними и объясни, почему по умолчанию стоит предпочитать value object.
2. Почему «граница агрегата = граница согласованности»? Что определяет минимальную границу агрегата и почему инвариант не может пересекать её?
3. Объясни, почему большой агрегат вредит параллелизму и масштабу. Свяжи с компромиссом «согласованность vs масштаб» из [1.5](../01-atributy-kachestva/01-05-upravlenie-kompromissami.md).

**Практика: поиск инвариантов и агрегатов**

4. Возьми кусок своей модели. Найди «голые» примитивы (деньги, email, даты, количества как number/string). Какие из них стоит сделать value objects и какие правила/валидацию они бы инкапсулировали?
5. Найди в своём домене один инвариант, который должен выполняться *всегда и немедленно*. Какой агрегат его защищает? Совпадает ли его граница с этим инвариантом — или агрегат слишком большой (конкуренция) / слишком маленький (инвариант пересекает границу)?

**Проектное задание**

6. Возьми анемичную модель из раздела §4 (или похожую из своего кода) и преврати её в богатый агрегат: value object для значений, методы вместо сеттеров, защита инварианта в корне, ссылка на другие агрегаты по id, доменное событие. Назови, какой инвариант теперь защищён и почему его нельзя обойти.
7. Прогони кейс из раздела §5 на своём домене: выбери инвариант немедленной согласованности, спроектируй агрегат точно по его границе, и явно реши, что вынести *наружу* через доменные события (то, что может быть согласовано позже). Объясни, как бы выглядел и чем был бы плох слишком большой агрегат для этого случая.

## 9. Что почитать дальше

- **Eric Evans. «Domain-Driven Design».** Первоисточник тактических блоков: сущности, value objects, агрегаты, репозитории, фабрики, доменные события.
- **Vaughn Vernon. «Implementing Domain-Driven Design» и «Effective Aggregate Design» (статьи).** Лучший разбор проектирования агрегатов и их размера — основа разделов §2.4–§2.5.
- **Vlad Khononov. «Learning Domain-Driven Design».** Современное, доступное изложение тактического DDD с акцентом на инварианты и границы согласованности.
- **Scott Wlaschin. «Domain Modeling Made Functional».** Моделирование домена через типы (value objects, недопущение невалидных состояний) — отлично ложится на TypeScript.
- **Martin Fowler, «AnemicDomainModel» (эссе).** Классическое описание главного антипаттерна главы.
