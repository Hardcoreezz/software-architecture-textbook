# Глава 8.1. SLI, SLO, SLA, бюджет ошибок

> Модуль 8. Надёжность, наблюдаемость, производительность
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

«Система должна быть надёжной» — пустые слова, пока не сказано, насколько надёжной и как это измерить. Надёжность — атрибут качества ([1.2](../01-atributy-kachestva/01-02-katalog-atributov-kachestva.md)), а атрибуты делают измеримыми: вместо «быстро» и «надёжно» — конкретные числа, как в сценариях качества ([1.4](../01-atributy-kachestva/01-04-scenarii-kachestva.md)). [Модуль 8](README.md) посвящён эксплуатации систем и начинается с языка целей надёжности: **SLI, SLO, SLA и бюджета ошибок**.

Без этого языка о надёжности спорят на эмоциях («падает слишком часто!»), а вопрос «выкатывать фичу или укреплять стабильность» решает тот, кто громче. SLI, SLO и бюджет ошибок дают объективную основу: сколько надёжности нужно, достигаем ли мы её и сколько риска можно себе позволить.

---

## 2. Теория

### 2.1. SLI: индикатор уровня сервиса

**SLI (Service Level Indicator)** — измеряемая метрика, которая показывает качество сервиса так, как его видит пользователь. Примеры: доля успешных запросов (availability), доля запросов быстрее порога (latency), доля корректных ответов.

Загрузка CPU — не SLI: пользователю она безразлична. Доля запросов, обслуженных быстрее 200 мс, — SLI: она отражает его опыт. Хороший SLI — отношение хороших событий ко всем, то есть доля, которую удобно выражать в процентах.

### 2.2. SLO: цель уровня сервиса

**SLO (Service Level Objective)** — цель по SLI, то есть значение, которое команда хочет держать: «99,9% запросов успешны за 30 дней», «99% запросов быстрее 200 мс». Это внутренняя цель команды.

SLO задаёт порог: выше него надёжность достаточна, ниже — проблема. Это «достаточно хорошо» ([1.5](../01-atributy-kachestva/01-05-upravlenie-kompromissami.md)), выраженное в числах.

### 2.3. SLA: соглашение об уровне сервиса

**SLA (Service Level Agreement)** — формальное обязательство перед клиентом, обычно в контракте, с последствиями за нарушение: компенсацией или штрафом. Например: «гарантируем 99,9% доступности, иначе вернём X% оплаты».

В отличие от SLO, за нарушение SLA приходится платить, поэтому SLA обычно мягче: если клиенту обещано 99,9%, внутренний SLO ставят строже, например 99,95%. Тогда внутренняя цель нарушается раньше контракта, и остаётся время среагировать. SLA есть не у всех систем: у внутренних часто только SLO.

### 2.4. 100% надёжности — неверная цель

**Цель надёжности — не 100%.** Причин три:
- *Невозможно.* Сеть ненадёжна, и рано или поздно отказывает всё ([4.1](../04-raspredelennye-sistemy/04-01-zabluzhdeniya-i-setevye-osnovy.md)); у зависимостей и инфраструктуры свои пределы.
- *Не нужно.* Пользователь не отличит 99,99% от 100%: его собственные сеть и устройство менее надёжны.
- *Дорого и тормозит.* Каждая следующая «девятка» обходится кратно дороже предыдущей и требует осторожности, которая замедляет изменения.

Правильная цель — достаточная надёжность, выведенная из нужд пользователей и бизнеса, а не максимальная. Это компромисс ([0.4](../00-professiya/00-04-arhitekturnoe-myshlenie.md)): надёжность против скорости развития и стоимости.

### 2.5. Бюджет ошибок: управление риском

Из SLO следует **бюджет ошибок (error budget)**: если SLO = 99,9%, то 0,1% запросов за период могут завершиться ошибкой. Это не провал, а разрешённый риск.

Бюджет превращает надёжность в правило для решений:
- Пока бюджет цел, можно рисковать: выкатывать фичи быстрее, экспериментировать. Тратить его стоит на рискованные, но ценные изменения.
- Когда бюджет тает, выкатывают осторожнее.
- Когда бюджет исчерпан, выкатку новых фич останавливают и занимаются стабильностью, пока бюджет не восстановится.

Так снимается вечный конфликт: разработка хочет фич, эксплуатация — стабильности. Бюджет ошибок становится общей валютой обеих сторон. SRE-практики, которые держатся на этом правиле, разобраны в [8.3](08-03-sre-praktiki.md).

## 3. Подходы

**Подход 1.** Определяй SLI с точки зрения пользователя — как долю успешных или быстрых запросов.

**Подход 2.** Выводи SLO из нужд пользователей и бизнеса, а не из принципа «чем больше девяток, тем лучше». Не гонись за 100% (§2.4).

**Подход 3.** Решай, выкатывать ли изменения, по расходу бюджета ошибок (§2.5), а не в споре.

**Подход 4.** Ставь SLO строже SLA, чтобы успеть среагировать до нарушения контракта (§2.3).

**Подход 5.** Измеряй SLI через наблюдаемость ([8.2](08-02-logi-metriki-trasing.md)) и отслеживай расход бюджета: без измерения SLO — просто число на бумаге.

**Подход 6.** Задавай SLO соразмерно ценности: для критичных путей строже, для некритичных мягче (risk-driven подход, [0.3](../00-professiya/00-03-obyazannosti-i-mify.md)).

## 4. Пример кода: SLI, SLO, бюджет ошибок

```typescript
// SLI: доля успешных запросов — качество глазами пользователя.
function availabilitySLI(goodRequests: number, totalRequests: number): number {
  if (totalRequests === 0) return 1; // нет запросов — нет нарушений
  return goodRequests / totalRequests; // доля от 0 до 1
}

// SLO: достаточная цель, а не 100%.
const orderApiSLO = {
  target: 0.999, // 99,9% успешных запросов
  window: "30d",
};

// Бюджет ошибок: 1 − SLO — допустимая доля ошибок.
function errorBudget(slo: number, totalRequests: number) {
  const allowedErrorRate = 1 - slo; // 0,1% при SLO 99,9%
  return {
    allowedErrors: Math.round(totalRequests * allowedErrorRate), // округляем, чтобы убрать погрешность float
    allowedErrorRate,
  };
}

// Решение о выкатке по расходу бюджета, а не по итогам спора.
function deploymentPolicy(actualErrors: number, budget: { allowedErrors: number }): string {
  if (actualErrors === 0) return "ship_fast"; // ошибок нет — бюджет цел (и нет деления 0/0 без трафика)
  const consumed = actualErrors / budget.allowedErrors;
  if (consumed < 0.5) return "ship_fast"; // бюджет цел — можно рисковать
  if (consumed < 1.0) return "ship_carefully"; // бюджет тает — осторожнее
  return "freeze_features_stabilize"; // бюджет исчерпан — стоп фичам, стабилизация
}

// SLO строже SLA: внутренняя цель нарушится раньше контракта.
const sla = 0.995; // обещано клиенту, с санкциями
const internalSLO = orderApiSLO.target; // 0.999
```

## 5. Развёрнутый кейс: от «падает слишком часто» к управляемой надёжности

Команда конфликтовала. Эксплуатация требовала: «Падает слишком часто, хватит фич, чините стабильность». Разработка отвечала: «Бизнес требует фич, всё работает нормально». Спорили на эмоциях, без данных.

**Шаг 1: SLI.** Определили, что важно пользователю: доля успешных запросов на оформление заказа и доля запросов быстрее 300 мс.

**Шаг 2: SLO.** Вместе с бизнесом выбрали достаточную надёжность — 99,9% успешных запросов за 30 дней. От 99,99% отказались: по расчёту это кратно дороже и затормозило бы развитие, а пользователь разницы не заметит. Внутренний SLO поставили строже клиентского SLA.

**Шаг 3: бюджет ошибок.** 0,1% запросов за 30 дней стали бюджетом ошибок. Расход бюджета начали измерять и привязали к нему правила выкатки:
- *Бюджет цел*: разработка спокойно выкатывает фичи и тратит бюджет на ценные изменения.
- *Бюджет тает*: выкатывают осторожнее.
- *Бюджет исчерпан*: новые фичи автоматически останавливаются, команда занимается стабильностью, пока бюджет не восстановится.

**Результат.** Бюджет ошибок стал общей валютой, и конфликт исчез. Эксплуатация перестала требовать вечной стабильности: пока бюджет цел, риск допустим и даже полезен для скорости. Разработка перестала игнорировать стабильность: исчерпав бюджет, она сама тормозит.

**Ошибка-контрпример.** Соседняя команда поставила цель «100% надёжности». Разработка боялась выкатывать, скорость упала, а 100% так и не достигли. Команда перешла на SLO 99,9% с бюджетом ошибок, разрешила себе допустимый риск и вернула скорость.

## 6. Антипаттерны и ловушки

**Надёжность как лозунг.** «Должно быть надёжно» без чисел — или SLO, который записан, но не измеряется. В обоих случаях цели фактически нет, и о надёжности спорят на эмоциях.

**Цель 100%.** Любой инцидент считается ЧП, а каждое изменение — угрозой идеалу; при этом цель недостижима (§2.4).

**SLI ради метрик, а не пользователя.** Надёжность меряют загрузкой CPU и памяти, хотя пользователю эти числа ничего не говорят.

**Нет бюджета ошибок.** SLO есть, но решения о выкатке принимают без оглядки на бюджет. Объективного правила нет, и споры «фичи или стабильность» возвращаются.

**Путаница SLO и SLA.** Внутреннюю цель приравнивают к обязательству перед клиентом. Запаса не остаётся: о проблеме узнают, когда контракт уже нарушен.

**Один SLO на всё.** Одна цель для критичного и некритичного: за некритичное переплачивают, а критичному надёжности не хватает.

## 7. Ключевые выводы (чеклист)

- [ ] Надёжность — измеримая величина, а не лозунг: задавай её числами.
- [ ] **SLI** — метрика с точки зрения пользователя: доля успешных или быстрых запросов.
- [ ] **SLO** — достаточная цель по SLI (например, 99,9% за 30 дней), выведенная из нужд бизнеса.
- [ ] **SLA** — внешнее обязательство с санкциями; SLO ставь строже SLA.
- [ ] **100% — не цель:** невозможно, не нужно, дорого и тормозит изменения.
- [ ] **Бюджет ошибок** (1 − SLO) — разрешённый риск: цел — рискуй, исчерпан — стабилизируй. Он снимает конфликт «фичи или стабильность».
- [ ] Измеряй SLI через наблюдаемость; задавай SLO соразмерно критичности пути.

## 8. Упражнения и вопросы

1. Чем различаются SLI, SLO и SLA? Почему SLO ставят строже SLA?
2. Почему 100% надёжности — неверная цель? Приведи три причины и объясни, почему каждая следующая «девятка» дороже предыдущей.
3. Что такое бюджет ошибок и как он управляет риском? Как он снимает конфликт «фичи или стабильность»?
4. Есть ли в твоей системе SLO? Если нет, как обсуждают надёжность — на эмоциях или по числам? Какой SLI отражал бы опыт твоих пользователей?
5. Если SLO есть, измеряется ли SLI на деле? Влияет ли бюджет ошибок на решения о выкатке, или это число на бумаге?
6. По коду из §4 посчитай бюджет ошибок при SLO 99,9% и 1 млн запросов. Что вернёт `deploymentPolicy` при 300, 900 и 1200 ошибках? Объясни логику.
7. Задай SLI и SLO для системы по выбору: выбери метрики с точки зрения пользователя, поставь достаточную (не 100%) цель с обоснованием из нужд бизнеса, определи бюджет ошибок и правило управления риском.
