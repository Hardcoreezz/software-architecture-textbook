# Глава 5.6. Паттерны интеграции (EIP)

> Модуль 5. Данные
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

Весь учебник к этому моменту разрезал систему на части — модули, сервисы, контексты (Модули 2, 3) — и научил хранить и обрабатывать данные в этих частях (Модуль 5). Но разрезанные части должны *общаться*: данные и сообщения текут между сервисами, хранилищами, событиями. Как именно? Здесь работает каноническая, проверенная десятилетиями библиотека — **паттерны интеграции предприятия (Enterprise Integration Patterns, EIP)** Хоупа и Вульфа. Это словарь и набор решений для того, *как сообщения движутся, маршрутизируются, преобразуются и собираются* между частями системы.

EIP закрывают Модуль 5, потому что они — клей, связывающий всё его содержимое: хранилища (5.1), производные данные (5.2), события (2.4), потоки и CDC (5.5), саги (4.5). Это не новая теория, а *каталог решений*, который превращает разрозненные приёмы («послать сообщение», «преобразовать формат», «собрать ответы») в общий язык с именами и проверенными реализациями. Архитектор, знающий EIP, не изобретает велосипед на каждой интеграции, а узнаёт форму задачи и берёт готовый паттерн — как с паттернами устойчивости (4.4).

Главная установка: **EIP — это словарь и каталог проверенных решений для движения сообщений, а не предписание усложнять.** Большинство паттернов нужны на *конкретной* интеграционной задаче; цель — узнавать форму («тут нужна маршрутизация по содержимому», «тут — сборка ответов») и брать соответствующий паттерн, а не лепить все подряд. И помни сквозную нить: интеграция через сообщения — это распределённость (Модуль 4), поэтому EIP живут вместе с идемпотентностью, доставкой at-least-once и устойчивостью.

## 2. Теория

### 2.1. Что такое EIP и зачем словарь

**EIP** — каталог из ~65 паттернов (книга Грегора Хоупа и Бобби Вульфа, 2003), описывающих интеграцию через *асинхронный обмен сообщениями*. Каждый паттерн — это именованное решение типовой задачи движения сообщений, с проверенной формой.

Зачем словарь (та же ценность, что у паттернов вообще): он даёт *общий язык* («это Content-Based Router», «нужен Aggregator») и *готовые решения*, чтобы не изобретать на каждой интеграции. EIP лежат в основе интеграционных фреймворков (Apache Camel, Spring Integration и др.) — это не абстракция, а рабочий инструментарий. Знание EIP — это насмотренность интеграции (эхо насмотренности стилей из Модуля 2).

### 2.2. Базовые строительные блоки

EIP строятся на нескольких фундаментальных понятиях:

- **Сообщение (Message):** единица данных, передаваемая между частями. Бывает *команда* (сделай), *событие* (произошло), *документ* (вот данные) — прямая связь с 2.4 (событие vs команда).
- **Канал сообщений (Message Channel):** «труба», по которой идут сообщения (очередь, топик). Развязывает отправителя и получателя (как в EDA, 2.4).
- **Конечная точка (Message Endpoint):** место, где приложение подключается к каналу (отправляет/принимает).

На этих блоках строятся остальные паттерны.

### 2.3. Маршрутизация (routing)

Паттерны, направляющие сообщения туда, куда нужно:

- **Content-Based Router (маршрутизатор по содержимому):** направляет сообщение по разным каналам в зависимости от его содержимого (заказ из ЕС → в европейский обработчик, из США → в американский).
- **Message Filter (фильтр):** пропускает только сообщения, удовлетворяющие условию, остальные отбрасывает.
- **Splitter (разделитель):** разбивает одно составное сообщение на несколько (заказ → отдельные сообщения по каждой позиции — для параллельной обработки).
- **Aggregator (агрегатор):** обратное — собирает несколько связанных сообщений в одно (собрать ответы по всем позициям обратно в один результат). Требует *состояния* (что собрать, когда считать полным) и стратегии завершения — связь с состоянием потоков (5.5).
- **Routing Slip / Process Manager:** ведёт сообщение через последовательность шагов — это, по сути, оркестрация (2.4) и основа оркестрационной саги (4.5).

### 2.4. Трансформация (transformation)

Паттерны, меняющие форму сообщения (мост между гетерогенными системами — заблуждение №8 из 4.1):

- **Message Translator (транслятор):** преобразует сообщение из одного формата/модели в другой. Это в точности антикоррупционный слой (ACL) из DDD (3.3) на уровне сообщений: переводит чужую модель в свою, защищая контекст.
- **Content Enricher (обогатитель):** добавляет в сообщение недостающие данные (по id товара дотягивает название из каталога).
- **Content Filter (прореживатель):** наоборот, убирает лишние/чувствительные поля.
- **Normalizer:** приводит сообщения разных форматов к одному каноническому.

Трансформация — ответ на гетерогенность (4.1, №8): системы говорят на разных «языках», EIP-трансформеры переводят между ними, не связывая их жёстко.

### 2.5. Надёжность и идемпотентность сообщений

Раз интеграция — это распределённость (Модуль 4), EIP включают паттерны надёжности, которые мы уже знаем под другими именами:

- **Guaranteed Delivery:** сообщение не теряется (персистентные каналы) — at-least-once (4.5).
- **Idempotent Receiver:** получатель безопасен к дублям — идемпотентность (4.5, 5.5), фундамент при at-least-once.
- **Dead Letter Channel:** сообщения, которые не удалось обработать, уходят в «мёртвый» канал для разбора — связь с обработкой ошибок потребителя (2.4) и устойчивостью (4.4).
- **Transactional Outbox / Messaging Bridge:** надёжная публикация (4.5 — outbox).

То есть EIP не отменяют Модуль 4, а *кодифицируют* его приёмы как именованные паттерны интеграции. Idempotent Receiver — это идемпотентность из 4.5; Dead Letter Channel — это обработка сбоя потребителя из 2.4.

### 2.6. Smart endpoints, dumb pipes — и осторожность с EIP

Важное предупреждение (прямая связь с 2.3 и уроком SOA). EIP исторически ассоциируются с *централизованными интеграционными шинами* (ESB), куда складывали всю логику маршрутизации и трансформации — и это породило антипаттерн «умной трубы» (2.3): шина становится узким горлышком и комом грязи. Современный подход (микросервисы, 2.3) — **«умные конечные точки, тупые трубы»**: логику держат в сервисах, а транспорт (канал) прост. EIP при этом не отменяются — они применяются *внутри* сервисов/конечных точек или как лёгкие шаблоны, а не как централизованная всемогущая шина. Используй паттерны EIP, но *не* строй на них единый ESB-монолит (антипаттерн, раздел 6).

### 2.7. EIP — это форма-под-задачу, не «применить все»

Как и со специализированными стилями (2.5) и паттернами устойчивости (4.4): EIP — *каталог под формы интеграционных задач*, а не чек-лист обязательного. Узнавай форму: «нужно направить по содержимому» → Content-Based Router; «собрать ответы воедино» → Aggregator; «перевести чужой формат» → Message Translator; «не потерять/не задвоить» → Guaranteed Delivery + Idempotent Receiver. Бери нужный паттерн под конкретную задачу. Лепить все подряд или строить тяжёлую интеграционную машину там, где хватит прямого вызова, — over-engineering (0.4). Большинство интеграций просты; EIP — для тех, что сложны.

### 2.8. Связь со всем модулем и учебником

EIP — клей, связывающий пройденное:
- **События (2.4):** сообщения, каналы — это инфраструктура EDA; routing/aggregation — обработка событийных потоков.
- **Saga (4.5):** Process Manager / Routing Slip — основа оркестрационной саги.
- **Идемпотентность, доставка (4.5):** Idempotent Receiver, Guaranteed Delivery, Dead Letter — кодификация надёжности.
- **ACL (3.3):** Message Translator — антикоррупционный слой на уровне сообщений.
- **Потоки/CDC (5.5):** конвейеры обработки сообщений — это EIP-паттерны (Splitter, Aggregator, Filter, Translator) в действии; pipeline-стиль (2.5) структурно.
- **Источник истины + производные (5.2):** трансформация и маршрутизация наполняют производные данные.

EIP — это, по сути, *именованный словарь* для всего, что мы строили вокруг сообщений и данных. Закрывая Модуль 5, они показывают: интеграция — не хаос ad-hoc решений, а набор узнаваемых форм с проверенными ответами.

## 3. Подходы

**Подход 1. Узнавай форму интеграционной задачи и бери паттерн.** «Направить по содержимому» → Content-Based Router; «собрать ответы» → Aggregator; «разбить на части» → Splitter; «перевести формат» → Message Translator; «дотянуть данные» → Content Enricher (2.3–2.4). Форма диктует паттерн, как и везде в учебнике.

**Подход 2. Используй EIP как общий язык.** Называй вещи их именами (Aggregator, Dead Letter Channel) — команда понимает мгновенно, не изобретая (2.1). Это насмотренность интеграции.

**Подход 3. Применяй надёжность как паттерны (не отменяй Модуль 4).** Guaranteed Delivery, Idempotent Receiver, Dead Letter Channel — именованные формы идемпотентности и доставки из 4.5/2.4 (2.5). Закладывай их в каждую асинхронную интеграцию.

**Подход 4. Умные конечные точки, тупые трубы — не строй ESB-монолит.** Применяй EIP *внутри* сервисов/эндпоинтов или как лёгкие шаблоны, не как централизованную всемогущую шину с логикой (2.6, урок 2.3). Транспорт прост, логика в сервисах.

**Подход 5. Не усложняй, где хватает прямого вызова.** EIP — для *сложных* интеграций. Большинство — простой синхронный вызов или одно событие (2.7). Не строй конвейер из десяти паттернов там, где достаточно одного вызова (over-engineering, 0.4).

**Подход 6. Используй интеграционные фреймворки.** Apache Camel, Spring Integration реализуют EIP — не пиши маршрутизаторы/агрегаторы/трансляторы с нуля (как не пишешь свой консенсус, 4.3, или устойчивость, 4.4). Бери проверенное, понимай, что под капотом.

**Подход 7. Связывай EIP с DDD и сагами.** Message Translator — это ACL контекста (3.3); Process Manager — оркестратор саги (4.5). Применяй EIP осознанно как реализацию архитектурных решений, а не как самоцель.

## 4. Пример кода: Splitter → обработка → Aggregator с идемпотентностью

Покажем композицию EIP на TypeScript: разбить заказ на позиции (Splitter), обработать каждую, собрать результаты (Aggregator), с идемпотентным получателем (4.5). Это типовой конвейер маршрутизации/сборки.

```typescript
// Композиция EIP: Splitter -> обработка позиций -> Aggregator (2.3).
// С Idempotent Receiver и Dead Letter Channel (2.5, надёжность из 4.5/2.4).

interface OrderMessage { orderId: string; items: { sku: string; qty: number }[]; }
interface ItemResult { orderId: string; sku: string; reserved: boolean; }

// SPLITTER: разбивает одно составное сообщение на несколько (2.3).
function splitOrder(order: OrderMessage): { orderId: string; sku: string; qty: number }[] {
  return order.items.map((i) => ({ orderId: order.orderId, sku: i.sku, qty: i.qty }));
}

// IDEMPOTENT RECEIVER: безопасен к дублям (2.5, фундамент 4.5).
class ReservationHandler {
  private processed = new Set<string>();
  async handle(msg: { orderId: string; sku: string; qty: number }): Promise<ItemResult> {
    const key = `${msg.orderId}:${msg.sku}`;
    if (this.processed.has(key)) return this.cached(key); // дубль (at-least-once) — не повторяем
    this.processed.add(key);
    const reserved = await this.inventory.reserve(msg.sku, msg.qty);
    return { orderId: msg.orderId, sku: msg.sku, reserved };
  }
  private cached(_key: string): ItemResult {/* вернуть прежний результат */ return null as any; }
}

// AGGREGATOR: собирает связанные сообщения обратно в одно (2.3). Требует СОСТОЯНИЯ (5.5):
// что собираем (по orderId), когда считать полным (все позиции пришли).
class OrderResultAggregator {
  private pending = new Map<string, { expected: number; results: ItemResult[] }>();

  start(orderId: string, expectedCount: number): void {
    this.pending.set(orderId, { expected: expectedCount, results: [] });
  }

  collect(result: ItemResult): { complete: boolean; results?: ItemResult[] } {
    const agg = this.pending.get(result.orderId);
    if (!agg) return { complete: false };
    agg.results.push(result);
    // Стратегия завершения: собрали все ожидаемые части (2.3).
    if (agg.results.length === agg.expected) {
      this.pending.delete(result.orderId);
      return { complete: true, results: agg.results }; // агрегат собран — публикуем итог
    }
    return { complete: false };
  }
}
```

А вот Content-Based Router и Message Translator (маршрутизация + трансформация, 2.3–2.4):

```typescript
// CONTENT-BASED ROUTER: направляет по содержимому (2.3).
function routeOrder(order: OrderMessage & { region: string }): string {
  return order.region === "EU" ? "channel.eu" : "channel.us"; // маршрут по полю содержимого
}

// MESSAGE TRANSLATOR = ACL контекста (3.3, 2.4): переводит ЧУЖОЙ формат в СВОЙ,
// не пуская чужую модель внутрь (как антикоррупционный слой из 3.3).
function translateExternalOrder(external: ExternalOrderDto): OrderMessage {
  return {
    orderId: external.order_ref, // перевод имён/формата чужой системы
    items: external.line_items.map((li) => ({ sku: li.product_code, qty: li.quantity })),
    // лишние/чужие поля external НЕ просачиваются — модель чиста (3.3).
  };
}
```

**Что показывает пример.** Это типовой интеграционный конвейер из именованных паттернов EIP (2.3). `splitOrder` — **Splitter**: разбивает составной заказ на позиции для параллельной обработки. `ReservationHandler` — **Idempotent Receiver** (2.5): дубль сообщения (неизбежный при at-least-once, 4.5) не задвоит резерв — это кодификация идемпотентности из 4.5 как паттерна интеграции. `OrderResultAggregator` — **Aggregator**: собирает результаты позиций обратно в один, для чего держит *состояние* (что собираем, когда полно — связь с состоянием потоков, 5.5) и стратегию завершения. `routeOrder` — **Content-Based Router**: направляет по содержимому. А `translateExternalOrder` — **Message Translator**, который есть антикоррупционный слой (3.3) на уровне сообщений: переводит чужой формат в свой, не пуская чужую модель внутрь. Заметь, что это не новые механизмы, а *именованные формы* уже знакомого: идемпотентность (4.5), ACL (3.3), состояние и сборка (5.5), маршрутизация событий (2.4). EIP дали им общий словарь и проверенные реализации (которые в реальности возьмёшь из Camel/Spring Integration, подход 6, а не напишешь руками).

## 5. Развёрнутый кейс: интеграция заказов с гетерогенными системами

Интернет-магазин интегрирует оформление заказа с несколькими системами разных форматов: внешний маркетплейс шлёт заказы в *своём* формате; заказ надо обработать по позициям; результаты собрать; направить в нужный склад по региону; не терять и не дублировать. Разберём через EIP.

**Приём из гетерогенной системы — Message Translator (ACL).** Маркетплейс шлёт заказы в своём формате (`order_ref`, `line_items`, `product_code`). Прямое использование его модели заразило бы наш контекст чужими понятиями (3.3). Решение — **Message Translator** (2.4): переводим внешний формат в нашу модель `OrderMessage` на входе, не пуская чужую модель глубже (раздел 4, `translateExternalOrder`). Это антикоррупционный слой (3.3) на границе интеграции — ответ на гетерогенность (4.1, №8).

**Маршрутизация по региону — Content-Based Router.** Заказы из ЕС должны идти в европейский склад/обработчик (регуляторика, локальность данных), из США — в американский. **Content-Based Router** (2.3) направляет по полю `region` (раздел 4, `routeOrder`). Никакого `if` в бизнес-логике — маршрутизация как явный паттерн.

**Обработка по позициям — Splitter + Aggregator.** Заказ резервируется *по позициям* (разные товары на разных складах), параллельно. **Splitter** разбивает заказ на позиции; каждая резервируется независимо; **Aggregator** собирает результаты обратно, чтобы решить судьбу заказа целиком (все зарезервированы → подтвердить; часть нет → сага компенсации, 4.5). Aggregator держит состояние и стратегию завершения (2.3, раздел 4).

**Надёжность — Guaranteed Delivery + Idempotent Receiver + Dead Letter.** Каналы персистентны (не теряем заказы — Guaranteed Delivery, 2.5); обработчики идемпотентны (дубль при at-least-once не задвоит резерв — Idempotent Receiver, 4.5); необработанные сообщения уходят в **Dead Letter Channel** для разбора (2.5, 2.4), а не теряются молча (урок 2.4 про молчаливый сбой потребителя).

**Связь с сагой.** Весь процесс (резерв → оплата → доставка) ведётся **Process Manager** — это оркестрационная сага (4.5, 2.3): EIP-паттерн Process Manager *и есть* оркестратор саги. Интеграция и согласованность бизнес-операции — две стороны одного.

**Поучительная ошибка: ESB-монолит.** Команда сначала собрала всю эту логику в *централизованную интеграционную шину* (ESB) — маршрутизация, трансформация, агрегация, оркестрация всех процессов в одном месте. Шина разрослась в ком грязи и стала узким горлышком: любое изменение интеграции правило центральный монолит, команды конфликтовали, отказ шины ронял все интеграции (повтор ошибки SOA, 2.3, 2.6). Лечение: «умные конечные точки, тупые трубы» (2.6) — логику EIP перенесли *в сервисы* (трансляция на входе сервиса, маршрутизация в сервисе-получателе), транспорт оставили простым. EIP не убрали — перестали централизовать.

**Мораль кейса.** Сложная гетерогенная интеграция разложилась на *узнаваемые формы* с именованными паттернами: чужой формат → Message Translator (=ACL, 3.3); маршрут по содержимому → Content-Based Router; обработка по частям → Splitter+Aggregator; надёжность → Guaranteed Delivery + Idempotent Receiver + Dead Letter (=4.5); процесс → Process Manager (=сага, 4.5). EIP дали словарь и проверенные решения вместо ad-hoc клубка. И ключевой урок (2.6): применяй EIP *в сервисах* (умные конечные точки), а не строй из них централизованный ESB-монолит — иначе повторишь ошибку SOA. Это синтез Модуля 5 и связь со всем учебником: интеграция — не хаос, а каталог форм, кодифицирующий события (2.4), ACL (3.3), саги и надёжность (4.5).

## 6. Антипаттерны и ловушки

**Изобретение велосипеда вместо EIP.** Городить ad-hoc маршрутизацию/сборку/трансляцию, не зная, что это известные паттерны с именами и реализациями (2.1, 2.7). Используй словарь и фреймворки (подход 2, 6), не изобретай.

**ESB-монолит / умная труба.** Стащить всю интеграционную логику в централизованную шину (кейс, 2.6, 2.3). Узкое горлышко, ком грязи, единая точка отказа — повтор ошибки SOA. «Умные конечные точки, тупые трубы»: логика в сервисах, транспорт прост.

**EIP как самоцель / лепить все подряд.** Строить тяжёлый конвейер из десяти паттернов там, где хватит прямого вызова или одного события (2.7, 0.4). EIP — для *сложных* интеграций; большинство просты. Узнавай форму, бери нужный паттерн.

**Игнор надёжности сообщений.** Асинхронная интеграция без Guaranteed Delivery / Idempotent Receiver / Dead Letter (2.5): теряем или дублируем сообщения, молчаливо роняем (4.5, 2.4). Интеграция — это распределённость; надёжность обязательна.

**Aggregator без стратегии завершения / с утечкой состояния.** Агрегатор, который не знает, когда «полно», или копит состояние незавершённых агрегатов бесконечно (2.3, эхо unbounded state из 5.5). Память течёт, сообщения зависают. Задавай стратегию завершения и таймауты.

**Трансляция, пускающая чужую модель внутрь.** Message Translator, который не изолирует (пропускает чужие понятия в контекст) — не ACL, а дырявая граница (3.3, 2.4). Перевод должен *защищать* модель, не просто копировать поля.

**Маршрутизация/логика, размазанная по коду.** Условная маршрутизация (`if region == ...`) в бизнес-логике вместо явного Content-Based Router (2.3). Логика интеграции прячется и дублируется. Выделяй в явный паттерн.

**Игнор связи EIP с архитектурой.** Применять EIP механически, не видя, что Message Translator — это ACL (3.3), а Process Manager — сага (4.5). Тогда паттерны живут отдельно от архитектурных решений и не согласованы с границами/контекстами.

## 7. Ключевые выводы (чеклист)

- [ ] **EIP** — каталог проверенных паттернов и **общий словарь** для движения сообщений между частями системы (маршрутизация, трансформация, сборка, надёжность).
- [ ] Базис: **сообщение** (команда/событие/документ), **канал** (труба), **конечная точка** — инфраструктура асинхронной интеграции (связь с EDA, 2.4).
- [ ] **Маршрутизация:** Content-Based Router, Filter, Splitter, Aggregator, Process Manager (= оркестратор саги, 4.5).
- [ ] **Трансформация:** Message Translator (= ACL контекста, 3.3), Content Enricher, Normalizer — ответ на гетерогенность (4.1, №8).
- [ ] **Надёжность кодифицирована как паттерны:** Guaranteed Delivery (at-least-once), Idempotent Receiver (идемпотентность 4.5), Dead Letter Channel (сбой потребителя 2.4) — это Модуль 4 под именами.
- [ ] **Умные конечные точки, тупые трубы:** применяй EIP в сервисах, **не строй ESB-монолит** (урок SOA, 2.3, 2.6).
- [ ] EIP — **форма-под-задачу, не «применить все»:** узнавай форму интеграции и бери паттерн; не усложняй, где хватит прямого вызова (0.4).
- [ ] Бери из **фреймворков** (Camel, Spring Integration), не пиши с нуля; связывай EIP с **DDD и сагами** (Translator=ACL, Process Manager=сага).
- [ ] EIP — **клей Модуля 5 и учебника:** кодифицируют события (2.4), ACL (3.3), саги и надёжность (4.5), конвейеры (5.5), производные данные (5.2).

## 8. Упражнения и вопросы для самопроверки

**Вопросы на понимание**

1. Зачем нужен словарь паттернов интеграции? Какую ценность даёт EIP помимо конкретных решений? Свяжи с ценностью паттернов вообще.
2. Объясни, почему Message Translator — это, по сути, антикоррупционный слой (3.3), а Process Manager — оркестратор саги (4.5). Что это говорит о связи EIP с архитектурой?
3. Почему «умные конечные точки, тупые трубы» важнее, чем ESB-монолит? Какой урок SOA (2.3) тут повторяется?

**Практика: распознавание паттернов**

4. Возьми интеграцию в своей системе (между сервисами, с внешней системой, через очередь). Какие EIP в ней работают (возможно, неявно)? Есть ли там маршрутизация, трансформация, сборка, надёжность — и реализованы ли они как явные паттерны или ad-hoc?
5. Найди в своей системе интеграцию с гетерогенной/внешней системой. Есть ли Message Translator (ACL), защищающий вашу модель, или чужая модель просачивается внутрь? Есть ли Idempotent Receiver и Dead Letter для надёжности?

**Проектное задание**

6. Возьми код-пример из раздела 4. Добавь Content Enricher: входящему заказу не хватает названий товаров (есть только sku) — дотяни их из каталога перед обработкой. Где в конвейере он встанет (до Splitter или после)? Какой паттерн надёжности нужен, если каталог временно недоступен (4.4)?
7. Спроектируй интеграционный конвейер для задачи по выбору (приём заказов из нескольких маркетплейсов разных форматов; рассылка уведомлений по разным каналам; агрегация данных из нескольких сервисов). Назови используемые EIP по именам, укажи, где Translator=ACL и Process Manager=сага, и где паттерны надёжности. Проверь себя: не превращаешь ли в ESB-монолит и не усложняешь ли там, где хватит прямого вызова.

## 9. Что почитать дальше

- **Gregor Hohpe, Bobby Woolf. «Enterprise Integration Patterns».** Первоисточник — каталог всех ~65 паттернов с диаграммами и примерами. Настольная книга по интеграции.
- **enterpriseintegrationpatterns.com.** Сайт с кратким изложением каждого паттерна — удобный справочник (как ISO 25010 для атрибутов в 1.2).

- **Sam Newman. «Building Microservices», главы об интеграции.** EIP в контексте микросервисов и «умных конечных точек, тупых труб» (2.6, 2.3).
- **Chris Richardson. «Microservices Patterns».** Process Manager / оркестрация саги, обмен сообщениями, надёжность — мост к 4.5.
