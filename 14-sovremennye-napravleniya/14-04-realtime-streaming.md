> Модуль 14. Современные направления

## 1. Зачем это нужно

Всё больше систем обрабатывают данные *в реальном времени*, потоково: аналитика на лету, обнаружение мошенничества в момент транзакции, real-time персонализация, IoT-телеметрия, live-дашборды, реакция на события немедленно. Это **real-time и стриминговые архитектуры** — обработка *непрерывных потоков* данных по мере поступления, в отличие от классической запрос-ответной (6.1) или batch (5.5) обработки. Глава 5.5 уже ввела batch vs stream и Kafka (6.3); здесь — углубление в *архитектуру* потоковых систем: чем они отличаются, паттерны потоковой обработки, и где real-time оправдан, а где это лишняя сложность.

Глава закрывает Модуль 14. Real-time/стриминг — кульминация асинхронности (2.4 EDA, 6.3 Kafka) и потоковой обработки (5.5). Прямое продолжение: batch/stream (5.5 — event time, окна, состояние), EDA (2.4), Kafka/лог (6.3), async (6.1). Как современное направление — с оговоркой о контексте (real-time по нужде, не везде).

Установка: **real-time/стриминговые системы обрабатывают непрерывные потоки данных по мере поступления, что отличается от запрос-ответной и batch обработки (состояние, время, окна, бесконечность потока); применяй real-time, где немедленность даёт ценность, а не везде — это несёт сложность.**

## 2. Теория

### 2.1. Чем стриминг отличается

Три парадигмы обработки (углубление 5.5, 6.1):
- *Запрос-ответ (6.1):* синхронно, по запросу, один результат сейчас.
- *Batch (5.5):* обработка *ограниченного* набора данных пакетом, периодически (ночной отчёт) — данные накапливаются, потом обрабатываются.
- *Стриминг (real-time):* обработка *непрерывного, бесконечного потока* событий *по мере поступления* — низкая задержка (8.4), реакция немедленна.

Ключевые отличия стриминга (что меняет архитектуру):
- *Бесконечность потока (5.5):* данные не «заканчиваются» (в отличие от batch) — обработка непрерывна, нет «конца» для агрегации (отсюда окна, 2.3).
- *Состояние:* потоковая обработка часто *с состоянием* (агрегаты, счётчики по потоку) — состояние надо хранить/восстанавливать (сложнее stateless 8.5).
- *Время (event time vs processing time, 5.5):* когда событие *произошло* vs когда *обработано* — расходятся (задержки, переупорядочивание); важно для корректности.
- *Низкая задержка (8.4):* ценность в немедленности — обработать за миллисекунды/секунды, не часы (batch).

Стриминг — это непрерывная обработка бесконечного потока с состоянием и вниманием ко времени, не «быстрый batch».

### 2.2. Где real-time оправдан

Real-time несёт сложность (2.5), поэтому — *где немедленность даёт ценность* (по нужде, как всё):
- *Обнаружение мошенничества:* поймать мошенническую транзакцию *в момент*, не в ночном отчёте (поздно — деньги ушли).
- *Real-time персонализация/рекомендации:* реагировать на поведение сейчас.
- *Мониторинг/алертинг (8.2):* реагировать на проблему немедленно, не через час.
- *IoT/телеметрия:* обрабатывать поток датчиков на лету.
- *Live-дашборды, торговля (13.4):* данные сейчас.

Где real-time *не* нужен (batch проще, 5.5): периодические отчёты, аналитика, где задержка в часы приемлема, ETL. Не делай real-time, где batch достаточно — стриминг сложнее (2.5). Немедленность должна давать *ценность* (13.1), оправдывающую сложность.

### 2.3. Паттерны потоковой обработки (углубление 5.5)

Из 5.5, подробнее:
- *Окна (windowing):* поток бесконечен (2.1) — агрегируешь по *окнам* (за последнюю минуту/час, скользящие/фиксированные). «Сумма транзакций за 5 минут» — окно. Окна решают проблему «когда агрегировать бесконечный поток».
- *Event time и поздние данные (5.5):* агрегируй по *времени события* (когда произошло), не обработки — иначе неверно при задержках/переупорядочивании. Обрабатывай *поздние* данные (пришли с опозданием) — watermarks (отметки прогресса времени).
- *Состояние и его управление:* потоковая обработка с состоянием (агрегаты, джойны потоков) — состояние хранится, восстанавливается при сбое (checkpoints) для отказоустойчивости (8.6).
- *Гарантии доставки (6.3, 4.5):* at-least-once + идемпотентность (4.5) или exactly-once (effectively-once) — как в EDA (2.4), важно для корректности агрегатов.
- *Backpressure (4.4):* если обработка не успевает за потоком — обратное давление (4.4), не падение.

Это специфика, которой нет в запрос-ответе/batch: время, окна, состояние потока, поздние данные.

### 2.4. Архитектуры: Lambda, Kappa (из 5.5)

Из 5.5, в контексте real-time:
- *Lambda-архитектура:* *два* пути — batch (точный, медленный, полная история) + stream (быстрый, приблизительный, real-time), результаты объединяются. Даёт и real-time, и точность, но *дублирует* логику (две системы — сложность).
- *Kappa-архитектура:* *один* поток для всего (только стриминг), переобработка через replay лога (6.3 — Kafka хранит, можно перечитать). Проще (одна система), но всё через стриминг.

Выбор (0.4): Lambda — real-time + batch-точность ценой дублирования; Kappa — единообразие ценой «всё в стриминге». По нужде (5.5). Современный тренд — к Kappa/унификации (стриминг как основа), где возможно.

### 2.5. Сложность и по нужде

Real-time/стриминг несёт *существенную* сложность (эхо распределёнки 4.x, EDA 2.4):
- Состояние, окна, event time, поздние данные, гарантии, backpressure (2.3) — сложнее запрос-ответа/batch.
- Операционная сложность (стриминговая инфраструктура — Kafka 6.3, процессоры потоков; отказоустойчивость состояния 8.6).
- Отладка распределённого потока (наблюдаемость 8.2, трейсинг асинхронности 2.4).

Поэтому — *по нужде* (как микросервисы 2.3, EDA 2.4, ML 14.3): real-time, где немедленность даёт ценность (2.2), оправдывающую сложность; где batch (5.5)/запрос-ответ достаточны — не усложняй. «Сделаем всё real-time» без нужды — over-engineering (как преждевременные микросервисы 2.3). Немедленность ↔ сложность — компромисс (0.4).

### 2.6. Связь с пройденным и Модулем 14

Real-time/стриминг углубляет batch/stream (5.5 — окна, event time, состояние, Lambda/Kappa), EDA (2.4 — события, async, гарантии), Kafka/лог (6.3 — поток, replay), async (6.1); использует устойчивость (4.4 — backpressure), отказоустойчивость (8.6 — checkpoints состояния), наблюдаемость (8.2), гарантии доставки (4.5 — идемпотентность); по нужде (как 2.3, 2.4). Это четвёртое и последнее современное направление (Модуль 14): кульминация асинхронной/потоковой обработки. Завершает Модуль 14 (современные направления: platform engineering 14.1, data mesh 14.2, ML/AI 14.3, real-time 14.4) — все строятся на фундаментальных принципах учебника, применяемых по нужде. Дальше — Модуль 15 (Capstone): синтез всего.

## 3. Подходы

**Подход 1.** Понимай отличия стриминга (2.1): непрерывный бесконечный поток, обработка по мере поступления, состояние, время (event vs processing), низкая задержка — не «быстрый batch».

**Подход 2.** Применяй real-time, где немедленность даёт ценность (2.2): мошенничество, персонализация, мониторинг, IoT, торговля. Где batch (5.5) достаточен (отчёты, периодическая аналитика) — не усложняй.

**Подход 3.** Используй паттерны потоковой обработки (2.3, 5.5): окна (агрегация бесконечного потока), event time + поздние данные (корректность), управление состоянием (checkpoints для отказоустойчивости 8.6), гарантии доставки (4.5), backpressure (4.4).

**Подход 4.** Выбирай Lambda/Kappa по нужде (2.4, 5.5): Lambda (real-time + batch-точность, ценой дублирования), Kappa (единый поток, проще, через replay 6.3). Тренд к унификации (Kappa) где возможно.

**Подход 5.** Учитывай сложность, применяй по нужде (2.5, 0.4): стриминг сложнее (состояние, время, операции); real-time только где немедленность оправдывает сложность. Не «всё real-time» (over-engineering как 2.3).

**Подход 6.** Опирайся на пройденное (2.6): устойчивость (4.4 backpressure), отказоустойчивость (8.6 checkpoints), гарантии (4.5 идемпотентность), наблюдаемость (8.2), Kafka/лог (6.3). Real-time — углубление async/stream, не отдельная магия.

**Подход 7.** Считай компромисс немедленность↔сложность (0.4, 2.5): немедленность даёт ценность (13.1), но несёт сложность/стоимость (9.5). Соразмерно (0.3): real-time для критичной немедленности, batch для остального.

## 4. Пример: стриминговая обработка (концептуально)

```
# REAL-TIME/СТРИМИНГ: непрерывный поток, обработка по мере поступления (2.1) — углубление 5.5.

# ПАРАДИГМЫ (2.1):
# Запрос-ответ (6.1): синхронно, один результат сейчас
# Batch (5.5):        ограниченный набор пакетом, периодически (ночной отчёт)
# Стриминг:           БЕСКОНЕЧНЫЙ поток по мере поступления, низкая задержка (8.4)

# ПРИМЕР: обнаружение мошенничества в РЕАЛЬНОМ времени (2.2 — немедленность даёт ценность).
[Поток транзакций (Kafka 6.3)] -> [Стримовый процессор] -> [алерт о мошенничестве СЕЙЧАС]
# Поймать в МОМЕНТ (не в ночном batch-отчёте — поздно, деньги ушли). Real-time ОПРАВДАН (2.2).

# ПАТТЕРНЫ потоковой обработки (2.3, 5.5):
process:
  - window: "5 minutes"          # ОКНО (2.3): агрегируем бесконечный поток по окнам
  - time: event_time             # EVENT TIME (5.5): когда ПРОИЗОШЛО, не обработано (корректность)
  - late_data: watermark         # ПОЗДНИЕ данные (5.5): пришли с опозданием — обработать
  - state: checkpointed          # СОСТОЯНИЕ (2.3): агрегаты с состоянием, checkpoints (отказоуст. 8.6)
  - delivery: at_least_once + idempotent  # ГАРАНТИИ (4.5): effectively-once для корректности агрегатов
  - backpressure: enabled        # BACKPRESSURE (4.4): не успеваем за потоком → обратное давление, не падение

# АРХИТЕКТУРЫ (2.4, 5.5):
# Lambda:  batch (точный) + stream (быстрый) — real-time + точность, ценой ДУБЛИРОВАНИЯ логики
# Kappa:   один поток, переобработка через replay лога (6.3) — проще, единообразно

# ПО НУЖДЕ (2.5, подход 5): real-time, где немедленность даёт ЦЕННОСТЬ (мошенничество, мониторинг);
#   где batch (5.5) достаточен (отчёты) — НЕ усложнять (стриминг сложнее: состояние/время/операции).
# Компромисс немедленность↔сложность (0.4, 2.7).
```

**Суть:** стриминг (2.1) — обработка *бесконечного* потока по мере поступления (vs запрос-ответ 6.1 и batch 5.5), с низкой задержкой (8.4). Real-time оправдан, где немедленность даёт ценность (2.2 — мошенничество в момент, не в ночном отчёте). Паттерны (2.3, 5.5): *окна* (агрегация бесконечного потока), *event time* + поздние данные (корректность 5.5), *состояние* с checkpoints (отказоустойчивость 8.6), *гарантии* (at-least-once + идемпотентность 4.5 = effectively-once), *backpressure* (4.4). Архитектуры (2.4): Lambda (batch + stream, точность ценой дублирования), Kappa (один поток, проще, replay 6.3). По нужде (2.5): real-time где немедленность ценна, batch (5.5) где достаточно — стриминг сложнее (компромисс немедленность↔сложность 0.4).

## 5. Развёрнутый кейс: real-time обработка по нужде

Команда (интернет-магазин) рассматривала real-time обработку для нескольких задач.

**Где real-time оправдан (2.2).** Задача — обнаружение мошеннических транзакций. В batch (ночной отчёт, 5.5) мошенничество ловилось *поздно* — деньги уже ушли. Здесь *немедленность даёт ценность* (2.2): поймать в *момент* транзакции. Построили стриминговую обработку:
- *Поток транзакций* через Kafka (6.3, лог); стримовый процессор анализирует *по мере поступления* (2.1) — алерт о мошенничестве *сейчас*.
- *Паттерны (2.3, 5.5):* окна (агрегация поведения за 5 минут — всплеск транзакций), event time (когда произошло, корректность 5.5), состояние с checkpoints (отказоустойчивость 8.6), at-least-once + идемпотентность (4.5 — не пропустить/не задвоить), backpressure (4.4 — не падать при всплеске). Real-time здесь *оправдан* (немедленность критична).

**Где real-time НЕ нужен (2.2, 2.5).** Задачи — еженедельные отчёты по продажам, аналитика трендов. Здесь задержка в часы/день *приемлема* — немедленность *не даёт* ценности. Использовали *batch* (5.5, проще): не стали усложнять стримингом то, где batch достаточен (2.5). «Всё real-time» было бы over-engineering (как преждевременные микросервисы 2.3).

**Выбор архитектуры (2.4).** Для мошенничества нужна была и real-time реакция, и историческая точность. Рассмотрели Lambda (batch + stream — точность + real-time, ценой дублирования логики 2.4) vs Kappa (один поток + replay 6.3 — проще). Выбрали ближе к Kappa (единый поток с replay через Kafka 6.3) — проще операционно (одна система), переобработка через replay лога; дублирование логики Lambda (две системы) сочли излишней сложностью для их случая.

**Сложность учли (2.5).** Real-time несла существенную сложность (состояние, окна, event time, поздние данные, гарантии, backpressure 2.3; операционная сложность стриминговой инфраструктуры; отладка асинхронного потока 8.2/2.4). Применили её *только* где оправдано (мошенничество — немедленность критична), не везде. Опирались на пройденное (2.6): устойчивость (4.4), отказоустойчивость (8.6), гарантии (4.5), наблюдаемость (8.2), Kafka (6.3) — real-time оказался *углублением* async/stream, не отдельной магией.

**Результат.** Мошенничество ловилось в момент (real-time оправдан ценностью немедленности 2.2); отчёты/аналитика — batch (проще, где немедленность не нужна 2.5). Компромисс немедленность↔сложность (0.4) решён осознанно: стриминг для критичной немедленности, batch для остального (соразмерно 0.3).

**Ошибки-контрпримеры.** Команда А делала мошенничество в batch (ночной отчёт) — ловила поздно, теряла деньги (real-time был оправдан, но не применили). Команда Б, наоборот, сделала *всё* real-time «по моде» (отчёты, аналитику — где batch достаточен) — получила over-engineering (2.5, как преждевременные микросервисы 2.3): сложность стриминга (состояние, время, операции) без выгод немедленности там, где её ценность ноль. Команда В сделала стриминг, но проигнорировала event time и поздние данные (5.5) — агрегаты были неверны при задержках/переупорядочивании (некорректность). Уроки: real-time по нужде (где немедленность ценна), не везде (batch проще); учитывай специфику потока (event time, окна, состояние, гарантии).

**Мораль:** real-time/стриминг обрабатывает непрерывный бесконечный поток по мере поступления (2.1) — отличается от запрос-ответа (6.1) и batch (5.5) состоянием, временем (event time 5.5), окнами (2.3), бесконечностью. Применяй *по нужде* (2.5): где немедленность даёт ценность (мошенничество, мониторинг, IoT — 2.2), оправдывающую сложность; где batch достаточен (отчёты) — не усложняй (over-engineering). Используй паттерны (окна, event time, состояние с checkpoints, гарантии 4.5, backpressure 4.4); выбирай Lambda/Kappa (2.4) по нужде. Опирается на async/stream (5.5, 2.4, 6.3) и устойчивость/отказоустойчивость (4.4, 8.6). Компромисс немедленность↔сложность (0.4).

## 6. Антипаттерны и ловушки

**Real-time там, где нужна немедленность, но не применили.** Делать в batch то, где немедленность критична (мошенничество — 2.2, кейс А): ловишь поздно, теряешь ценность. Real-time, где немедленность даёт ценность.

**«Всё real-time» без нужды.** Делать стримингом то, где batch достаточен (отчёты, периодическая аналитика — 2.5, кейс Б): over-engineering (как преждевременные микросервисы 2.3), сложность без выгод немедленности. Real-time по нужде.

**Стриминг как «быстрый batch».** Игнорировать специфику потока (состояние, время, окна, бесконечность — 2.1): неверная обработка. Стриминг — непрерывный поток с состоянием и временем, не быстрый batch.

**Игнор event time и поздних данных.** Агрегировать по времени обработки, не события (5.5, кейс В): неверные агрегаты при задержках/переупорядочивании. Event time + поздние данные (watermarks).

**Состояние без отказоустойчивости.** Потоковое состояние без checkpoints (2.3, 8.6): сбой теряет состояние. Checkpoints для восстановления (8.6).

**Игнор гарантий доставки.** Стриминг без at-least-once + идемпотентности (4.5): потеря/задвоение событий → неверные агрегаты. Гарантии (effectively-once).

**Нет backpressure.** Стриминг без обратного давления (4.4): не успеваешь за потоком → падение/потеря. Backpressure (4.4).

**Lambda без нужды (дублирование).** Lambda (batch + stream) там, где Kappa (один поток) достаточен (2.4): дублирование логики, сложность. Kappa проще, где возможно.

## 7. Ключевые выводы (чеклист)

- [ ] **Стриминг/real-time** — обработка **непрерывного бесконечного потока** по мере поступления (vs запрос-ответ 6.1 и batch 5.5), низкая задержка (8.4); с состоянием и вниманием ко времени — не «быстрый batch».
- [ ] **Отличия:** бесконечность потока (5.5), состояние, **event time vs processing time** (5.5), низкая задержка. Меняют архитектуру.
- [ ] **Real-time по нужде** (2.2): где немедленность даёт **ценность** (мошенничество, мониторинг, IoT, торговля); где batch (5.5) достаточен (отчёты) — не усложняй.
- [ ] **Паттерны** (5.5): **окна** (агрегация бесконечного потока), **event time + поздние данные** (корректность), **состояние с checkpoints** (отказоустойчивость 8.6), **гарантии** (4.5 — at-least-once + идемпотентность), **backpressure** (4.4).
- [ ] **Lambda** (batch + stream — точность + real-time, ценой дублирования) vs **Kappa** (один поток + replay 6.3 — проще); по нужде (5.5), тренд к унификации.
- [ ] **Сложность существенна** (состояние, время, операции, отладка): применяй **по нужде** (как 2.3, 2.4); «всё real-time» — over-engineering. Компромисс немедленность↔сложность (0.4).
- [ ] Опирается на **async/stream** (5.5, 2.4, 6.3), **устойчивость** (4.4 backpressure), **отказоустойчивость** (8.6 checkpoints), гарантии (4.5), наблюдаемость (8.2) — углубление, не магия.
- [ ] Завершает Модуль 14: современные направления (platform 14.1, data mesh 14.2, ML 14.3, real-time 14.4) — эволюция фундаментальных принципов по нужде.

## 8. Упражнения и вопросы

1. Чем стриминг отличается от запрос-ответа (6.1) и batch (5.5)? Почему «не быстрый batch» (состояние, время, бесконечность)?
2. Где real-time оправдан, а где batch достаточен? Почему «всё real-time» — over-engineering?
3. Объясни окна, event time, поздние данные, backpressure в потоковой обработке. Зачем каждое?
4. Сравни Lambda и Kappa. Какой компромисс между ними?
5. Есть ли в твоей системе real-time/стриминг? Оправдан ли он (немедленность даёт ценность) или это могло бы быть batch? Или наоборот — где нужна немедленность, но делается batch (поздно)?
6. Возьми пример из раздела 4: спроектируй стриминговую обработку для задачи, где немедленность критична (мониторинг/мошенничество): окна, event time, состояние, гарантии, backpressure. Почему здесь не batch?
7. Для системы по выбору реши, какие задачи real-time (немедленность ценна), какие batch (достаточно); для real-time выбери паттерны и архитектуру (Lambda/Kappa) по нужде, учти сложность.
