# Глава 14.2. Data Mesh

> Модуль 14. Современные направления
> Уровень: Middle/Senior → подготовка к роли архитектора

---

## 1. Зачем это нужно

Platform engineering (14.1) применил идеи децентрализации, доменного владения и self-service к *инфраструктуре разработки*. **Data Mesh** (Жамак Дегани) применяет те же идеи к *данным* в масштабе организации. Проблема, которую он решает: традиционные централизованные данные (единое хранилище данных — data warehouse / data lake, обслуживаемое одной командой данных) не масштабируются организационно — центральная команда становится узким местом, оторвана от доменов (не знает контекст данных), данные теряют качество. Это та же болезнь, что монолитная разработка одной командой (12.1) или централизованная инфраструктура (14.1) — но для данных.

Глава — про data mesh как децентрализованный подход к данным: данные как продукт, доменное владение, self-service платформа данных. Прямое продолжение: децентрализация и владение (12.1 Конвей, 12.2 stream-aligned, 3.5 границы), self-service платформа (14.1), данные (Модуль 5), domain-driven design (3.3). Как современное направление — даётся с оговоркой о контексте (по нужде, для масштаба данных).

Установка: **data mesh применяет децентрализацию, доменное владение и self-service (как platform engineering 14.1) к данным: данные — продукт, которым владеют домены, на self-service платформе данных, — чтобы данные масштабировались организационно, а не упирались в центральную команду.**

## 2. Теория

### 2.1. Проблема централизованных данных

Традиционный подход к аналитическим данным в организации — *централизованный*: единое хранилище (data warehouse / data lake), обслуживаемое *одной* командой данных, которая собирает данные из всех систем (ETL), хранит и предоставляет для аналитики. Проблемы на масштабе (эхо монолита 12.1, централизованной инфраструктуры 14.1):
- *Центральная команда — узкое место:* все запросы на данные идут через неё; она не успевает (как тяжёлый governance 12.4, синхронная зависимость 6.1).
- *Оторванность от доменов:* команда данных не знает контекст данных доменов (что значат, как меняются) — данные теряют смысл/качество (как нарушение единого языка 3.3).
- *Размытое владение:* кто отвечает за качество данных? Доменные команды их производят, но не владеют в хранилище; центральная команда владеет, но не понимает. Никто не отвечает (как размытое владение 3.5).
- *Не масштабируется:* рост числа доменов/данных перегружает центр.

Это та же болезнь централизации, что Конвей решает для разработки (12.1) и platform engineering для инфраструктуры (14.1) — для данных.

### 2.2. Data Mesh: четыре принципа

**Data Mesh** — децентрализованный подход к данным, стоящий на *четырёх* принципах:

- **Доменное владение (domain ownership):** данные принадлежат *доменам* (командам, владеющим бизнес-возможностью 3.3, 3.5, 12.2), а не центральной команде. Кто производит данные и знает их контекст — тот и владеет (как stream-aligned команды владеют сервисами 12.2). Децентрализация (анти-2.1).
- **Данные как продукт (data as a product):** домен предоставляет свои данные *как продукт* для других (с качеством, документацией, SLA, удобством — как platform-продукт 14.1). Не «свалка данных», а продукт с потребителями (другие домены/аналитики).
- **Self-service платформа данных (self-serve data platform):** общая платформа (как IDP 14.1), дающая доменам инструменты предоставлять/потреблять данные self-service, скрывая инфраструктурную сложность данных (хранение, конвейеры 5.5). Снижает нагрузку доменов (как 14.1).
- **Федеративное вычислительное управление (federated computational governance):** стандарты (интероперабельность, безопасность 7.x, приватность 13.4, качество) — федеративные (общие правила, автоматизированные — как fitness functions 11.2 / governance 12.4), не централизованный контроль. Баланс автономии доменов и согласованности (как 12.4).

### 2.3. Аналогия с микросервисами и platform engineering

Data mesh — это *микросервисная декомпозиция применительно к данным* (3.x, 12.1) + platform engineering для данных (14.1):
- *Доменное владение* (2.2) = stream-aligned команды владеют данными своего домена (12.2), как сервисами (3.5); границы данных = границы доменов (3.3, Конвей 12.1).
- *Данные как продукт* (2.2) = как сервис предоставляет API (6.4), домен предоставляет данные с качеством/контрактом — X-as-a-Service (12.2) для данных.
- *Self-service платформа* (2.2) = IDP (14.1) для данных: скрывает сложность конвейеров (5.5), даёт self-service.
- *Федеративное управление* (2.2) = лёгкое управление (12.4): стандарты-guardrails, автоматизация (11.2), не централизованный контроль.

То есть data mesh — применение уже изученных принципов (децентрализация, владение, self-service, лёгкое управление) к *данным*. Не новая магия, а перенос проверенных идей в новую область.

### 2.4. Что даёт и когда нужен

Что даёт:
- *Масштабируемость данных организационно* (2.1): нет узкого места центральной команды; домены масштабируются независимо (как микросервисы 2.3).
- *Качество данных:* владеет тот, кто знает контекст (домен) — данные осмысленны, качественны (как единый язык 3.3).
- *Скорость:* self-service (как 14.1) быстрее тикетов к центральной команде.

Когда нужен (по нужде, как всё — 2.3 микросервисы, 14.1 платформа):
- *Оправдан:* большая организация, много доменов/данных, центральная команда данных стала узким местом (2.1). Тогда децентрализация окупается.
- *Избыточен:* небольшая организация, немного данных — централизованное хранилище проще и достаточно (data mesh — over-engineering, как преждевременные микросервисы 2.3). Несёт сложность децентрализации (как распределённые данные 5.2).

Data mesh — *организационно-архитектурный* сдвиг (не просто технология), требующий зрелости (как микросервисы 2.3, 12.1) — команды должны владеть данными, что меняет организацию (Конвей 12.1).

### 2.5. Связь с пройденным и риски

Data mesh применяет: децентрализацию/владение (12.1 Конвей, 12.2 stream-aligned, 3.5 границы); данные как продукт (~ API/сервис 6.4, 14.1 платформа-продукт); self-service платформу (14.1 IDP); федеративное управление (12.4 лёгкое управление, 11.2 fitness functions); данные (Модуль 5 — конвейеры 5.5, источник истины 5.2, polyglot 5.2). Это DDD (3.3) для данных + platform engineering (14.1) для данных. Риски:
- *Преждевременный data mesh* (2.4): для немногих данных — over-engineering (централизованное проще).
- *Data mesh без организационной зрелости* (2.4, как микросервисы без Конвея 12.1): домены не готовы владеть данными → хаос (распределённый монолит данных).
- *Без федеративного управления:* полная децентрализация без стандартов → несовместимость данных (зоопарк, как 12.4).

### 2.6. Связь с Модулем 14

Data mesh — второе современное направление (Модуль 14), показывающее *тот же паттерн*, что platform engineering (14.1): децентрализация, доменное владение, self-service, лёгкое управление — применённые к новой области (данные). Это иллюстрирует: современные направления — *эволюция фундаментальных принципов* (Конвей 12.1, DDD 3.3, platform 14.1, governance 12.4), не отдельная магия. Дальше Модуль 14 — архитектура ML/AI/LLM (14.3), real-time/стриминг (14.4). Data mesh связывает данные (Модуль 5) с организацией (Модуль 12) и платформами (14.1) — по нужде, для масштаба.

## 3. Подходы

**Подход 1.** Применяй data mesh, когда централизованные данные стали узким местом (2.1, 2.4): большая организация, много доменов/данных, центральная команда не справляется. Децентрализация — для масштаба.

**Подход 2.** Дай доменам владеть их данными (2.2): кто производит и знает контекст (stream-aligned команды 12.2, домены 3.3), тот владеет — как сервисами (3.5). Децентрализация владения.

**Подход 3.** Делай данные продуктом (2.2): домен предоставляет данные с качеством, документацией, контрактом, SLA — для потребителей (другие домены/аналитики), как platform-продукт (14.1). Не свалка.

**Подход 4.** Строй self-service платформу данных (2.2, как IDP 14.1): инструменты предоставлять/потреблять данные self-service, скрывая сложность конвейеров (5.5). Снижает нагрузку доменов.

**Подход 5.** Федеративное управление (2.2, как 12.4): общие стандарты (интероперабельность, безопасность 7.x, приватность 13.4, качество), автоматизированные (fitness functions 11.2), не централизованный контроль. Баланс автономии и согласованности.

**Подход 6.** Применяй по нужде, не преждевременно (2.4): для немногих данных централизованное хранилище проще (data mesh — over-engineering, как микросервисы 2.3). Требует организационной зрелости (Конвей 12.1).

**Подход 7.** Понимай как перенос принципов (2.3): data mesh = DDD (3.3) + микросервисы (12.1) + platform engineering (14.1) + лёгкое управление (12.4) для данных. Не магия, а проверенные идеи в новой области.

## 4. Пример: data mesh vs централизованные данные (концептуально)

```
# DATA MESH: децентрализация данных (как микросервисы 12.1 + platform engineering 14.1 для данных).

# ЦЕНТРАЛИЗОВАННО (2.1, проблема): одна команда данных — узкое место, оторвана от доменов.
[Домен Заказы] --\
[Домен Каталог] ---> [Центральная команда данных] -> [единое хранилище] -> аналитика
[Домен Платежи] --/
# Центр: узкое место (все через неё 6.1), не знает контекст доменов (качество падает 3.3),
#   размытое владение (никто не отвечает 3.5). Не масштабируется (2.1).

# DATA MESH (2.2): домены ВЛАДЕЮТ данными, предоставляют как ПРОДУКТ, на self-service платформе.
[Домен Заказы]   -> data product "заказы" (качество, контракт, SLA) --\
[Домен Каталог]  -> data product "каталог"                          ---> потребители
[Домен Платежи]  -> data product "платежи"                          --/  (другие домены, аналитика)
        |                  |                  |
        v                  v                  v
   [Self-serve платформа данных (14.1)]: инструменты предоставлять/потреблять self-service,
        скрывает сложность конвейеров (5.5) — снижает нагрузку доменов (как IDP 14.1)
        |
   [Федеративное управление (12.4/11.2)]: стандарты (интероперабельность, безопасность 7.x,
        приватность 13.4) — автоматизированы (fitness functions 11.2), не централизованный контроль

# ЧЕТЫРЕ ПРИНЦИПА (2.2): доменное владение + данные как продукт + self-service платформа + федерат. управление.
# = DDD (3.3) + микросервисы (12.1) + platform engineering (14.1) + лёгкое управление (12.4) для ДАННЫХ (2.3).

# ПО НУЖДЕ (2.4, подход 6): для МНОГИХ доменов/данных (центр — узкое место);
#   для немногих — централизованное проще (data mesh = over-engineering, как микросервисы 2.3).
```

**Суть:** централизованные данные (2.1) — одна команда данных собирает всё в единое хранилище: узкое место (все через неё 6.1), оторвана от контекста доменов (качество падает 3.3), размытое владение (3.5), не масштабируется. Data mesh (2.2) децентрализует по *четырём принципам*: домены *владеют* своими данными (как сервисами 3.5, 12.2); предоставляют как *продукт* (качество, контракт, SLA — для потребителей, как 14.1); на *self-service платформе данных* (как IDP 14.1 — скрывает сложность конвейеров 5.5); с *федеративным управлением* (стандарты автоматизированы 11.2, не централизованный контроль — как 12.4). Это DDD (3.3) + микросервисы (12.1) + platform engineering (14.1) + лёгкое управление (12.4) для данных (2.3). По нужде (2.4): для многих доменов/данных, для немногих — централизованное проще.

## 5. Развёрнутый кейс: децентрализация данных

Большая организация (много доменов, растущие данные) страдала от централизованных данных и перешла к data mesh.

**Проблема: централизованное узкое место (2.1).** Единое хранилище (data lake), обслуживаемое *одной* командой данных. На масштабе (десятки доменов, растущие данные):
- *Узкое место:* все запросы на данные/аналитику шли через центральную команду — она не успевала (как синхронная зависимость 6.1, тяжёлый governance 12.4).
- *Оторванность:* команда данных не знала контекст данных доменов (что значат поля заказов, как меняется каталог) — данные в хранилище теряли смысл и качество (нарушение единого языка 3.3).
- *Размытое владение:* домены производили данные, но не владели ими в хранилище; центр владел, но не понимал — за качество не отвечал никто (3.5).
- Не масштабировалось — рост доменов перегружал центр.

**Решение: data mesh (2.2).** Применили четыре принципа (раздел 4):
- *Доменное владение (2.2):* данные передали во владение *доменам* (stream-aligned командам 12.2, владеющим бизнес-возможностями 3.3) — кто производит и знает контекст, тот владеет (как сервисами 3.5). Децентрализация (обратный Конвей 12.1 для данных).
- *Данные как продукт (2.2):* каждый домен предоставлял свои данные *как продукт* — с качеством, документацией, контрактом, SLA (как platform-продукт 14.1) — для потребителей (другие домены, аналитики). Не свалка, а продукт.
- *Self-service платформа данных (2.2, как 14.1):* построили общую платформу (как IDP 14.1), дающую доменам self-service инструменты предоставлять/потреблять данные, скрывая сложность конвейеров (5.5) — снизила нагрузку доменов (как platform engineering 14.1).
- *Федеративное управление (2.2, как 12.4):* стандарты (интероперабельность данных, безопасность 7.x, приватность 13.4 — критично для регулируемых данных, качество) — федеративные, автоматизированные (fitness functions 11.2), не централизованный контроль. Баланс автономии доменов и согласованности (как 12.4).

**Результат.** Данные масштабировались организационно (нет узкого места центра — домены независимы, как микросервисы 2.3); качество выросло (владеет знающий контекст домен 3.3); скорость выросла (self-service быстрее тикетов к центру, как 14.1). Data mesh решил болезнь централизации — применив децентрализацию, владение, self-service, лёгкое управление (те же принципы, что 12.1, 12.2, 14.1, 12.4) к данным (2.3).

**По нужде (2.4).** Это была *большая* организация со многими доменами и растущими данными — data mesh окупился (центр был реальным узким местом 2.1). Требовалась организационная зрелость (домены готовы владеть данными — Конвей 12.1).

**Ошибки-контрпримеры.** Организация А (небольшая, немного данных) внедрила data mesh «по моде» — получила over-engineering (2.4): сложность децентрализации данных (как распределённые данные 5.2) без выгод, централизованное хранилище было бы проще и достаточно (как преждевременные микросервисы 2.3). Организация Б внедрила data mesh *без организационной зрелости* (домены не готовы владеть данными, нет stream-aligned команд — против Конвея 12.1) — получила хаос («распределённый монолит данных», аналог 12.1): данные децентрализованы, но домены не владеют толком. Организация В децентрализовала *без федеративного управления* (2.5) — несовместимость данных между доменами (зоопарк, как 12.4 без стандартов). Уроки: data mesh по нужде (масштаб), с организационной зрелостью (Конвей 12.1), с федеративным управлением (12.4) — иначе over-engineering или хаос.

**Мораль:** data mesh применяет децентрализацию, доменное владение, self-service и федеративное управление (те же принципы, что Конвей 12.1, stream-aligned 12.2, platform engineering 14.1, лёгкое управление 12.4) к *данным*: домены владеют данными как продуктом на self-service платформе с федеративными стандартами. Решает узкое место централизованных данных (2.1) для масштаба. По нужде (2.4): для многих доменов/данных окупается, для немногих — over-engineering (централизованное проще); требует организационной зрелости (Конвей 12.1) и федеративного управления (12.4). Это перенос проверенных принципов в область данных, не магия.

## 6. Антипаттерны и ловушки

**Централизованное узкое место.** Одна команда данных обслуживает всё на масштабе (2.1, кейс): узкое место (6.1), оторванность от контекста (качество 3.3), размытое владение (3.5), не масштабируется. Децентрализация (data mesh) по нужде.

**Преждевременный data mesh.** Внедрять для немногих доменов/данных «по моде» (2.4, кейс А): over-engineering — сложность децентрализации (5.2) без выгод. Централизованное хранилище проще для небольшого масштаба.

**Data mesh без организационной зрелости.** Децентрализовать данные, когда домены не готовы владеть (нет stream-aligned команд, против Конвея 12.1) (2.4, кейс Б): хаос, «распределённый монолит данных». Требует зрелости (Конвей 12.1).

**Без федеративного управления.** Полная децентрализация без общих стандартов (2.5, кейс В): несовместимость данных, зоопарк (как 12.4 без governance). Федеративные стандарты (автоматизированные 11.2).

**Данные как свалка, не продукт.** Домены предоставляют данные без качества/контракта/документации (2.2): потребители не могут пользоваться. Данные как продукт (качество, SLA, как 14.1).

**Нет self-service платформы.** Децентрализовать без платформы данных (2.2, 14.1): домены тонут в сложности конвейеров (5.5) каждая сама (как команды без IDP 14.1). Self-service платформа.

**Data mesh как просто технология.** Считать data mesh технологией, а не организационно-архитектурным сдвигом (2.4): без изменения владения (Конвей 12.1) технология не поможет. Это сдвиг владения и организации.

## 7. Ключевые выводы (чеклист)

- [ ] **Data mesh** применяет децентрализацию, доменное владение, self-service, федеративное управление (как Конвей 12.1, stream-aligned 12.2, platform engineering 14.1, лёгкое управление 12.4) к **данным**.
- [ ] Решает проблему **централизованных данных** (одна команда данных): узкое место (6.1), оторванность от контекста (качество 3.3), размытое владение (3.5), не масштабируется.
- [ ] **Четыре принципа:** **доменное владение** (домены владеют своими данными, как сервисами 3.5), **данные как продукт** (качество/контракт/SLA, как 14.1), **self-service платформа данных** (как IDP 14.1, скрывает сложность 5.5), **федеративное управление** (стандарты автоматизированы 11.2, не контроль — как 12.4).
- [ ] Это **перенос проверенных принципов** в область данных: DDD (3.3) + микросервисы (12.1) + platform engineering (14.1) + лёгкое управление (12.4). Не магия.
- [ ] **Даёт:** масштабируемость данных организационно (нет узкого места), качество (владеет знающий контекст), скорость (self-service).
- [ ] **По нужде, не преждевременно** (2.4): для многих доменов/данных окупается; для немногих — over-engineering (централизованное проще, как микросервисы 2.3).
- [ ] **Требует организационной зрелости** (Конвей 12.1 — домены готовы владеть) и **федеративного управления** (12.4); иначе хаос («распределённый монолит данных») или несовместимость.
- [ ] Организационно-архитектурный сдвиг (владение, организация), не просто технология.

## 8. Упражнения и вопросы

1. Какую проблему централизованных данных решает data mesh? Чем она похожа на болезнь монолита (12.1) и централизованной инфраструктуры (14.1)?
2. Назови четыре принципа data mesh. Как каждый соотносится с уже изученным (владение 12.2/3.5, продукт 14.1, платформа 14.1, управление 12.4)?
3. Почему data mesh — перенос принципов, а не новая магия? Когда он оправдан, а когда over-engineering?
4. Как устроены данные в твоей организации — централизованно (одна команда данных) или децентрализованно? Есть ли узкое место/оторванность от контекста?
5. Если централизованно и это узкое место — готовы ли домены владеть данными (организационная зрелость, Конвей 12.1)? Что предоставлять как data product?
6. Возьми пример из раздела 4: для своей организации продумай доменное владение данными (кто чем владеет), что предоставить как продукт, что в self-service платформу, какие федеративные стандарты.
7. Реши, нужен ли data mesh для организации по выбору: много ли доменов/данных, центр — узкое место? Есть ли зрелость? Если да — как применить четыре принципа; если нет — почему централизованное достаточно.
